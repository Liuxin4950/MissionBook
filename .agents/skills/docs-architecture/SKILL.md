# 架构文档维护

帮助项目建立清晰、准确、易于维护的架构文档，让开发者和 AI 能够快速理解系统结构、模块职责及核心数据流。
文档默认建在项目根目录的 `docs/`（或 `Docs/`）下。

## 核心原则

- **以代码为准**：文档描述当前真实实现，不凭记忆或旧文档推测。
- **按业务划分**：围绕功能域组织文档，不按具体技术栈强制划分。
- **单一事实来源**：同一事实只在一处详细定义，其他文档通过链接引用。
- **按需读取**：优先读取相关模块和代码，必要时再扩大范围。
- **保持简洁**：记录设计逻辑、工作机制、核心流程和关键约束，不记录无价值的实现细节。

## 文档组织

优先遵循项目现有的文档目录。如果尚未建立架构文档体系，可参考：

```
docs/
├── README.md              顶部模块导航目录 + 全局架构
├── <领域>/                如:前端，后端，设计，运维等
│   └── <模块>/
│       ├── README.md      模块入口：顶部细分文档目录 + 模块架构
│       ├── <子领域>.md    细分文档
│       └── ...
```

约定：

- 文档根目录和模块目录统一使用 README.md 作为入口，不再使用总览.md：顶部是下一层的目录，下方写本层架构内容。领域目录默认只承担分类和组织作用，不强制创建 README.md。
- 根 README.md：顶部是按领域分组的模块导航，下方写全局架构（系统整体结构、跨模块核心数据流）。
- 模块 README.md：顶部是细分文档目录，下方写模块架构（职责、文件地图、数据流、陷阱约束）。
- 一个模块对应一个相对独立的功能域。领域目录用于归类，模块边界以业务功能为准；跨端功能优先保持完整模块，不因前后端技术差异而机械拆分。
- 领域目录根据项目实际情况划分，例如设计、前端、后端、运维或具体业务领域。
- 细分文档按具体主题命名，不使用序号前缀。
- 横切关注点（如统一认证、跨服务通信、日志规范）独立建档。
- 单篇文档建议不超过 500 行，内容过多时按子领域拆分。

## 文档编写规范

### 1. 根 README.md 骨架

```markdown
# 项目架构

> 项目整体定位与架构简介。

## 模块导航

| 领域 | 模块 | 职责 |
|---|---|---|
| <领域> | [<模块>](相对路径) | 模块职责 |

## 全局架构

说明系统整体组成、核心服务、技术边界及模块之间的关系。

## 跨模块数据流

使用文字流程图描述系统级核心业务链路。

## 全局约束

只记录真正跨模块的设计约定，写简短条目；已有横切文档的用链接引用，不重复细节。模块内部约束放在模块 README。
```

### 2. 模块 README.md 骨架

每个模块的 README.md 使用以下结构，目录在顶部：

```markdown
# <模块名>架构

> 一句话职责

## 目录

| 文档 | 内容 |
|---|---|
| [子领域.md](相对路径) | 该文档负责说明的内容 |

## 模块职责

说明模块解决什么问题、负责什么、不负责什么，以及涉及的端、服务和模块边界。

## 文件地图

按子领域分组，使用表格：

| 文件 | 职责 |
|---|---|
| [文件路径](相对路径) | 文件负责的具体职责 |

必要时补充关键类、方法及行号，引用必须真实存在。

## 数据流概览

使用文字流程图（ASCII 缩进树或箭头）描述核心链路。

字段名、方法名、事件名与代码保持一致。

## 陷阱与约束

记录已验证的设计限制、容易踩坑的地方和必须遵守的规则。
```

### 3. 细分文档骨架

```markdown
# <子领域>

> 说明本文档的职责与内容范围。

## <主题一>

根据实际内容描述设计逻辑、实现机制和关键代码。

## <主题二>

使用表格、流程图或代码引用说明复杂逻辑。

## 陷阱与约束

记录该子领域特有的注意事项。
```

### 4. 表达规范

- 使用中文，技术名词、代码标识符保留原始名称。
- 重点解释为什么这样设计，以及系统实际上如何工作。
- 数据流优先使用文字流程图，不依赖外部图片。
- 代码引用使用相对路径，采用可点击的 Markdown 链接。
- 同一事实不要在多篇文档中重复定义。
- 区分当前实现、设计约定和历史遗留问题。
- 不确定的内容先核实，不将推测写成事实。

## 工作流程

### 1. 了解项目

阅读项目指令、根 README.md 和相关模块 README.md，了解现有文档组织方式。

### 2. 判断变更

- 已有模块发生架构或业务事实变化：更新原文档。
- 出现新的功能域：创建模块文档或更新已有相关文档。
- 仅修改内部实现，文档描述仍然准确：不修改文档。

### 3. 核对代码

阅读本次变更涉及的源码，必要时追踪调用方、数据模型、配置和测试，确认实际行为与依赖关系。

### 4. 更新文档

优先修改原有内容，不重复追加说明。

- 文件变化：更新文件地图。
- 模块内部数据流变化：更新模块 README 的流程图。
- 模块边界变化：更新模块职责和相关索引。
- 新增或移除细分文档：更新模块 README 的目录。
- 新增、移除、移动或重命名模块：更新根 README 的导航及相关引用。
- 跨模块架构或数据流变化：更新根 README 的全局架构与跨模块数据流。
- 出现新的设计限制：补充陷阱与约束。

### 5. 验证

检查文档与源码的一致性，以及文件路径、代码引用、Markdown 链接、章节锚点和模块索引。

无法完成的检查明确说明，不得声称验证通过。

## 完成汇报

简要说明：
- 更新或新增的文档。
- 主要记录的架构变化。
- 已完成的验证。
- 尚未确认的问题。
