# Mission Book — 数据落地与平台

本文档约束存储、导入协议、文件和平台集成。业务规则以[领域模型](领域模型.md)为准，字段以[数据模型](数据模型.md)为准。平台条目是待实现、待实测的交付要求，不代表当前设备已经验收。

## 本机 Web 开发预览（2026-10-22 授权）

用户授权为当前已实现的任务创建、今天页查询与刷新增加本机浏览器预览。它不扩大 Windows / Android 正式交付清单，也不表示浏览器通知、附件和备份已实现。

浏览器复用 Drift 表结构、仓储、事务和业务入口，通过配套 Worker + SQLite WASM 使用 OPFS 或 IndexedDB 存储。数据库按浏览器配置与访问来源独立；不读取原生文件、不跨端同步。必须使用同一依赖版本编译 Worker，不能静默将纯内存连接当作持久化成功。清除网站存储、隐私模式和浏览器回收可能影响保留；配置与实测边界见[Web 浏览器预览](../开发/Web浏览器预览.md)。

## 1. 核心表与关系

技术选型为 Drift + SQLite。完整交付只包含以下八张核心表；按切片逐步添加，不要求第一阶段全部建立。

| 对象 | 表 |
| --- | --- |
| Goal | goals |
| GoalNode | goal_nodes |
| Mission | missions |
| MissionScheduleRevision | mission_schedule_revisions |
| ExecutionPlan | execution_plans |
| ExecutionEvent | execution_events |
| Evidence | evidence |
| FailureRecord | failure_records |

字段使用 snake_case 映射数据模型中的语义字段。ExecutionPlan 的有序 steps 可编码为 JSON Text 整体读写，不参与结构化查询；大纲树必须规范化为 GoalNode，不用原始 JSON 驱动业务。

启用外键，历史关系不使用级联物理删除。需要唯一约束：

- execution_plans.mission_id。
- mission_schedule_revisions 的 (mission_id, revision_number)。
- execution_events 的 (mission_id, sequence)，以及每 Mission 至多一个 START、一个 END。
- failure_records 的 (mission_id, trigger)。
- evidence.supersedes_evidence_id 的非空值唯一，避免修正链分叉。

外键不能表达的同 Goal、同 Mission、事件序列、跨任务 RUNNING 限制、截止互斥等，在事务内校验，并通过真实数据库测试验证。

## 2. 存储格式与事务

| 数据 | 保存方式 |
| --- | --- |
| ID | 客户端生成的全局唯一 Text |
| 枚举 | 稳定字符串名称，不使用 ordinal |
| DateTime | UTC 时间戳，统一精度为毫秒 |
| scheduledDate | 独立日历日期 YYYY-MM-DD，不冒充 UTC 时刻 |
| timeZone | 排期使用的 IANA 时区标识 |
| 计划分钟数 | 正整数分钟 |
| 派生时长 | 统一以整数毫秒计算，展示时格式化 |
| 路径 | 私有目录相对 storageKey |

所有[领域业务操作](领域模型.md#9-查询事实与业务原子操作)及 Goal/节点创建编辑都通过 Application Workflow 进入数据库。跨表操作只有一个提交边界；页面、通知回调不分别拼接更新。

2026-10-23 当前实现说明：任务创建、日期查询和详情查询由 application/missions/mission_service.dart 的 MissionService 统一承接，业务操作名称不要求各自定义一个类。entities 保留业务实体与查询组合，以类注释注明来源；真正的表结构在 data/local/tables/，数据库行到业务对象的转换和事务仍由 Drift 仓储实现。此组织调整不改变持久化字段、schema 版本、业务规则或原子边界。

写命令串行化，并在已取得写入权限的事务内重读事实、分配 sequence/revisionNumber、校验并写入，防止两个 START 或两个提交同时通过旧快照。后台通知操作也必须经过同一规则，不能用独立的无校验写入路径。

截止操作与首次提交互斥：取得写事务后捕获一次操作时刻，校验截止并用该时刻作为 submittedAt；提交前取得的截止检查不能跨异步选文件或复制文件复用。通过校验后即使磁盘提交跨过截止瞬间，仍以这次事务内的时刻判断。

发现已经到期时，只提交唯一 FailureRecord，不写任何首批 Evidence；业务结果返回“材料已超时”，不能把超时记录随提交错误一起回滚。EndMission 在已到期时也原子保存 END 和超时记录。

通知调度在业务提交后执行，失败不回滚业务数据。附件准备在事务前完成，事务失败保留当前草稿；后续由安全清理回收真正无引用文件。

## 3. Schema、启动与备份

仓库处于重新实现阶段，首个持久化切片从 schemaVersion = 1 开始。此后只要已经存在需要保留的本地数据，每次表结构变化必须升级版本并迁移；学习阶段也不把自动删库作为升级方案。

- 保存可复现的 Schema 快照；每次增加切片的表或列都处理版本变化。
- 启动先打开与迁移数据库、校验关键关系、补算已到期强制材料，再发布可用查询和对账通知。
- 初始化失败提供明确错误与重试；未知枚举、不支持的新版本或损坏关系不静默猜测，不覆盖用户数据。
- 不正常启动注入示例数据，不提供正式一键清空全部数据。
- 升级测试必须保留既有事件、材料、附件引用和关联关系；文档规定的业务模型不意味着这些表已经存在。

当前备份导出由 Me 发起：生成一个包含数据库一致快照、全部 Formal Evidence 引用附件及 manifest.json 的归档。manifest 记录备份格式版本、数据库版本和导出时刻；不包含未提交草稿、临时缓存或通知调度元数据。

数据库快照必须使用数据库支持的一致备份方式，或在暂停写入并完成必要的日志处理后复制；不能在写入期间只拷贝主数据库文件而忽略日志。附件是不可变的，按快照中的引用收集并校验存在性；缺失时导出明确失败，不返回看似完整的备份。

导出不修改源数据；归档完成后再交给系统保存入口。当前不实现备份恢复、导入合并或跨设备接力，也不把备份格式当作 AI 上下文协议。

## 4. Evidence 附件

附件字段和类型组合完全遵循[数据模型](数据模型.md#51-evidence)。storageKey 示例为 attachments/<missionId>/<attachmentId>.png，不能包含盘符、绝对路径、父目录跳转或来源 content URI。

- 用户选择或拍照后，校验实际大小不超过 20 MiB（20 × 1024 × 1024 字节），复制到私有目录的新唯一键。
- 来源文件名只作展示，不直接拼成可执行路径。图片类型需能被实际解码，其他文件可作为 FILE 保存。
- 首次提交仅把已经准备好的相对键写入 Evidence，不复制第二份文件。每条修正使用新键，不能覆盖旧附件。
- 草稿删除或明确丢弃时，只删除当前草稿拥有且无 Formal Evidence 引用的副本。
- 启动完成数据库恢复后、创建任何新草稿之前，清理应用管理的 attachments 目录中无正式引用的遗留文件。清理期间不允许并发创建/提交草稿。
- 不清理目录以外文件、不删除存在正式引用的键。附件缺失要显示明确错误；清理失败不抹掉数据库记录。
- 草稿未进入数据库；进程退出不保证恢复。正常离开编辑页有内容时必须提醒用户确认。

## 5. Goal Outline 导入

### 5.1 协议与结构

JSON 是外部输入协议。当前只支持用户确认后创建一个新 Goal 和完整大纲，不支持 Merge / Replace。外部 AI 可以生成该格式，但应用不据此声称数据作者一定是 AI。

```json
{
  "schema": "mission-book.goal-outline",
  "version": 1,
  "goal": {
    "title": "掌握 Flutter 应用开发",
    "description": "能够独立开发和维护 Flutter 应用",
    "why": "完成 Mission Book 并形成真实项目能力"
  },
  "nodes": [
    {
      "key": "navigation",
      "title": "Navigation",
      "description": "页面导航与 Route Stack",
      "children": [
        { "key": "route-stack", "title": "Route Stack" }
      ]
    }
  ]
}
```

### 5.2 字段和校验

| 对象 | 允许字段 | 规则 |
| --- | --- | --- |
| Root | schema、version、goal、nodes | 全部必须；schema 为固定字符串，version 为整数 1，nodes 可空 |
| Goal | title、description、why | title 必须为 Trim 后非空 String；其他为可省略的 String |
| Node | key、title、description、children | key/title 必须为 Trim 后非空 String；children 省略等同空数组 |

所有未列入字段都明确拒绝，防止拼写错误或外部 status / id 等业务字段被悄悄忽略。可选字段若提供则必须符合类型，不接受 null 冒充 String / Array。key 仅用于这次输入校验，整棵导入树内唯一，不保存为运行时身份。

文件和粘贴文本使用相同限制：UTF-8 内容最多 2 MiB（2 × 1024 × 1024 字节），最多 500 个节点，根节点为第 1 层、最大深度 12 层。解析前检查字节大小；解析及遍历遇到超限立即停止，报告错误路径和限制。

确认时由应用生成全局 ID、父子关系、同级 orderIndex 和时间；Goal 初始 ACTIVE，节点 archivedAt 为空。忽略不了的非法字段必须在预览前拒绝，不让外部输入指定运行时状态。

### 5.3 导入路径

```text
系统选择 .json 文件 / 粘贴文本 → 解码与完整校验
→ Goal 与 Tree 预览 → 用户确认 → 单事务保存 Goal + GoalNode[]
```

用户确认前不写业务数据。读取失败、非法格式、取消预览或任意节点保存失败都不留下半条导入。当前不保存原始 JSON 审计快照；导入后只查询规范化记录。

## 6. 计时与应用生命周期

页面定时器只刷新显示；Focus 等计算读取真实事件。关闭应用、页面切换、系统回收不会隐式写 PAUSE / END。重启按事件恢复，无后台定时器也不能丢失已经保存的时间线。

材料截止采用启动/回到前台/前台定时检查补算，不要求应用关闭期间在截止瞬间修改数据库。未完成草稿可能丢失，已提交事实和正式附件必须保留。

绝对时刻以 UTC 保存；排期时区负责固定时间、默认截止和“可以开始”标签。Today 的计划日期按 scheduledDate，完成活动按 END 在设备当前时区的日期分组，见[本地应用规格](本地应用规格.md#46-页面进度和日期)。修改设备时区不重新安排已保存的绝对开始/截止时刻。

## 7. 通知与权限

### 7.1 通知的事实与元数据

通知标题、执行摘要、按钮由 MissionPhase 和事件投影。FIXED 未开始任务安排一次开始提醒；FLEXIBLE 不安排。开始、取消或改期后清理不再有效的旧提醒。

“延后 15 分钟”是独立的提醒偏好，不是改期或执行事件。平台适配层在本地应用设置中持久化 missionId、scheduleRevisionId、snoozedUntil 及该版本是否已经提醒；它们不进入八张领域表，也不参加业务统计。提醒偏好是用户设置，系统通知才是可重建的投影；不能声称仅凭业务排期就能恢复延后选择。保存偏好失败要提示，不能假装延后成功。

启动/系统重启时，按业务事实及有效提醒偏好对账。存在有效 snoozedUntil 时保留它，不用原 fixedStartAt 覆盖；旧版本、已开始或已取消任务的偏好丢弃。过期而尚未送达的有效提醒补发一次，已送达不反复弹出。通知设置损坏时明确提示延后偏好可能丢失；可按原排期恢复提醒并提示可能重发，不改写业务事实。

每次延后都将该版本当前提醒的送达标记重置为未送达，实际触发提醒后再标记；“调度成功”不等于已经送达。业务提交和系统送达之间无法做数据库原子事务，异常情况下提醒可重发，操作本身仍须幂等。

### 7.2 动作

- 开始提醒提供“开始 / 延后 15 分钟”；开始仍须通过 StartMission 和单个 RUNNING 检查。
- RUNNING 显示标题、Focus 摘要和“停止”；PAUSED 显示标题、Focus 摘要和“继续”。多个 PAUSED 时各自可进入任务，展示样式按平台验收。
- “停止”只在 RUNNING 时写 PAUSE，再打开 END 确认；取消确认保持 PAUSED。已经 PAUSED 时打开确认不再重复 PAUSE。
- END 后清理执行通知；待补材料不继续显示执行计时通知。
- 通知 payload 带 Mission ID 和所依据的排期版本或执行 sequence；旧动作先重查，不允许延迟的旧按钮修改后来状态。
- 每次执行事件提交（包括 EXTEND）后刷新通知与 payload，确保合法的新按钮携带最新 sequence。
- 系统回调及前台按钮调用相同 Workflow。不能因为跳转失败而静默 END。

### 7.3 平台验收边界

Android 按实际目标系统处理通知与精确提醒权限；未授权或系统限制时业务仍可保存和手动执行，明确显示提醒可能延迟或不可用。系统重启后恢复有效调度；用户“强行停止”后不承诺后台提醒，重新手动打开后恢复对账。具体厂商、省电限制和通知可见性必须真机验证。

Windows 使用本地通知适配，是否需要打包身份及操作按钮的实际行为以当前分发方式实测为准。未经测试不声称退出进程后仍可接收所有操作。通知负责提醒，计时正确性不依赖其常驻。

## 8. 文件入口与品牌资产

Windows 使用系统文件对话框，Android 文件导入/附件使用系统文档选择入口，不要求广泛外部存储访问。拍照按实际实现所需权限处理；拒绝后可改为文件选择。

品牌和布局见[设计稿说明](../ui设计手册/README.md)。最终交付需要 1024 px 品牌母版、Android 启动/自适应/单色和通知图标、Windows 多尺寸 ICO，以及可重复生成脚本。图中页脚版本不约束工程版本；不同裁切下不得丢失主体，图标与通知在真实平台验收。
