# 排期、课次与导入配置

状态：2026-10-27 设计稿。字段见[协议](协议与字段.md)，数据提交见[事务设计](事务与数据结构.md)。

## 1. 先分清三个时间

| 时间 | 谁提供 | 是否导入 |
| --- | --- | --- |
| 计划日期 scheduledDate | 用户排期约束或外部 AI | 是 |
| 计划开始 fixedStartAt | 用户明确的课次安排 | FIXED 必须 |
| 实际开始 START.occurredAt | 应用取得写权限后发生的真实操作 | 否 |

例如：上海 11 月 2 日 19:00 上课，45 分钟：

~~~json
{
  "scheduledDate": "2026-11-02",
  "timePolicy": "FIXED",
  "fixedStartAt": "2026-11-02T19:00:00+08:00",
  "plannedDurationMinutes": 45
}
~~~

在默认 Asia/Shanghai 下，保存的 fixedStartAt 是 2026-11-02T11:00:00Z。如果系统 19:03 才执行自动开始，START 应记 19:03，不倒填 19:00。19:45 是计划时段的边界，不是已经发生的 END。

FLEXIBLE 只有日期和时长，不存在确定的几点开始；必须由用户手动开始。若需要每个任务都有确定启动时刻，就让外部 AI 为每个任务生成 FIXED 及 fixedStartAt，而不是给 FLEXIBLE 填一个空时间。

## 2. 时区、偏移与日历检查

1. 解析有效 timeZone，必须存在于应用使用的 IANA 时区数据中。
2. 严格核对年月日、时分秒；不能只调用 DateTime.parse，因为它会接受越界日期并自动顺延。依据：[Dart 官方解析说明](https://api.dart.dev/dart-core/DateTime/parse.html)。
3. FIXED 的绝对开始时刻换算到有效时区后，日期必须等于 scheduledDate。
4. 输入为非 Z 偏移时，还要把原始当地时间及偏移与 IANA 规则往返核对；例如上海 19:00+09:00 会提示偏移不匹配。输入为 Z 时视为纯绝对时刻，仅检查换算后的计划日期。
5. 夏令时重复时刻必须靠明确偏移消除歧义，不存在的当地时刻拒绝；不能静默移动一小时。
6. 保存后设备切时区不改动绝对开始和截止；日期仍按该排期捕获的时区解释。

默认截止或批量移期构造当地日历时间时也要往返核对。有些地区可能跳过午夜或整天；此时要求显式给出合法截止或日期，不能把库自动归一化当作用户意图。

## 3. 三种材料策略

| 有效策略 | 验收方向 | 材料截止 | 执行结束后 |
| --- | --- | --- | --- |
| SELF_REPORT | 可选 | 不允许出现 | 报告完成即可关闭 |
| OPTIONAL_EVIDENCE | 可选 | 不允许出现 | 完成时选择直接结束或稍后交材料 |
| REQUIRED_EVIDENCE | 必须非空 | 显式给出或展开默认值 | 完成后按真实提交或超时关闭 |

强制材料省略 evidenceDeadlineAt 时：

~~~text
取 scheduledDate 的下一个日历日
→ 在有效 timeZone 中构造该日 00:00
→ 检查当地时刻存在且无歧义
→ 转换成 UTC，显式显示在预览中
~~~

不能用“当天起点 + 24 小时”代替日历计算。显式截止需晚于提交事务中的 now；FIXED 还需晚于 fixedStartAt，FLEXIBLE 还需晚于排期日当地起点。

建议预览另外提示“截止早于计划时段结束”的不合理安排，但不擅自把原有领域下限提高为“必须晚于开始+时长”。确实需要提高时，应统一调整手工创建和导入规则。

强制材料截止只约束完成后的材料首提，不是任务执行的强制停止时刻；未开始任务不会因材料截止自动产生失败。

## 4. 每周重复课程怎样落地

**首版建议以具体课次作为唯一正式导入形态。** 例如两周周一、周三 19:00 学习，遇 11 月 4 日停课：

~~~text
课程约束：2026-11-02 至 2026-11-15，周一/周三，19:00，45 分钟
排除日期：2026-11-04

最终生成 3 个 Mission：
2026-11-02 19:00
2026-11-09 19:00
2026-11-11 19:00
~~~

每次有自己的 key、排期、方案和执行历史。它们可关联同一知识点，也可按课标顺序分配不同节点。课程间的顺序不能只写“第 2 周”让应用猜日期。

| 作者侧配置 | 外部生成或预处理时要做什么 |
| --- | --- |
| 学期开始/结束日期 | 形成有限边界，禁止无限生成 |
| 上课星期、单双周、每天时段 | 按课次计算具体日期和开始时刻 |
| 放假、考试、已占用时间 | 排除或明确调整，不静默顺延 |
| 课标顺序、每节目标、任务数量 | 分配知识点，核对有无遗漏和多排 |
| 可用时间和每天上限 | 生成后重新计算总分钟数和冲突 |
| 预习/练习/复习频率 | 分别生成独立任务，保留各自目的 |

这些配置属于外部 AI 的输入约束，不是 goal-package v1 的额外字段。外部 AI 可能算错星期、次数和时区，应用仍需校验具体结果，用户仍需检查是否忠实覆盖课标。

如果实际使用证明“每天动态生成下一次”或“统一修改尚未开始的所有课次”不可缺少，再引入有限重复规则、例外日期、生成游标和模板到实例的关系。届时需要专门的模板协议和幂等生成，不能仅给 Mission 加 recurrence 文本就宣称完成。

## 5. 用户本地导入选项

课程内容与日期由文件提供；怎样处理冲突由用户在导入区选择。**以下是设计中的本地选项，不允许 AI 通过 JSON 设置。**

| 选项 | 首版建议默认 | 行为 |
| --- | --- | --- |
| targetMode | CREATE_NEW | 创建一个新目标；不自动合并、替换旧目标 |
| pastSchedulePolicy | BLOCK | 过去日期的 FLEXIBLE 或已错过整段的 FIXED 必须处理后再提交 |
| allowDueAutoStart | false | 正处于可自动开始时段的 FIXED 默认阻止；允许时明确提示提交后可能立即开始 |
| fixedOverlapPolicy | BLOCK | 包内或与已有未开始固定计划重叠，先调整；用户可显式接受重叠 |

“保留过期计划”意味着仍创建没有执行事实的待开始任务，不补 START / END、时长、失败和完成率；强制材料截止已过的输入仍拒绝，不能被该选项豁免。

“允许当前时段立即开始”只允许沿用现有调度规则，不保证立即开始：存在 RUNNING 时仍保留当前任务并通知处理。不得承诺“保留在待开始且不让调度器启动”，除非将来另行实现明确的启用机制。

没有关闭自动开始、设置逐任务提醒、改变全局提前提醒或自动结束的隐藏选项。全局提醒继续由用户在设置中控制，导入不能改变它。

## 6. 冲突怎样判断

- 对 FIXED 使用半开 UTC 区间 [fixedStartAt, fixedStartAt + duration)。区间端点相接不算计划重叠，跨午夜也按真实时刻比较。
- 包内使用按开始时间排序的扫描；检测和标记可做到 O(M log M)，若要列举全部 K 对冲突，还需 O(K) 输出成本，并限制界面一次展示的数量。
- 与已有任务只读相关时段、最新排期、未取消且无 START 的候选；不按当前筛选页面里“看得见的任务”计算。
- 已有 RUNNING 不以原计划结束时刻假定它已经结束，单独提示执行资源占用；PAUSED 的未来恢复不可预测。
- FLEXIBLE 只有日期，不能凭空假定它占某个小时；可以汇总每日总负荷并提示。
- 计划冲突并非数据库非法关系。用户明确允许重叠时保留全部任务，但自动开始仍严格限制一个 RUNNING。

预览后其他入口可能新增/改期/开始任务。提交事务必须重读相关事实；新的阻断冲突返回 PREVIEW_STALE，在原位更新预览后再确认，不能沿用旧确认内容。

## 7. 过期与批量移期

首版可先提供“导出错误明细、修改 JSON 再预览”；批量移期是便利功能，不应成为正确导入的前置依赖。

如实现“整体移后 N 个日历日”：

1. 对 scheduledDate 按当地日历移动。
2. FIXED 保留当地几点几分，重新用 IANA 规则生成绝对时刻；不简单加 N×24 小时。
3. 默认截止重新按新日期生成；显式截止只有用户选择“同步移动”时按对应日历移动，并在预览逐项展示。
4. 重算节假日、偏移、截止和所有冲突，重新确认；最终修改后的内容参与摘要。
5. 这是尚未提交草稿的转换。若该 packageId 已成功导入，再改内容不能冒充同一请求，需另定义更新流程或明确新建副本。

## 8. 预览必须显示的完整信息

| 区域 | 内容 |
| --- | --- |
| 目标与树 | 目标说明、动机、节点数、层级、未安排任务的节点 |
| 任务清单 | 标题、完整节点路径或“直接属于目标”、日期、时区、固定/自选、计划分钟 |
| 方案展开 | objective、全部 steps、notes、材料策略与验收方向 |
| 时间明细 | 当地开始和 UTC、明确的默认/自定截止、可立即自动开始项 |
| 汇总 | 总任务数、每日负荷、固定/自选数量、三种材料策略数量 |
| 异常 | 过期、偏移问题、重复键、冲突、强制截止错误、未覆盖的课标节点 |
| 提交结果 | 创建的新目标和条数；重复包则指向已经存在的目标 |

技术字段如 UUID、回执摘要不挤进普通操作区；发生包身份冲突时再提供可复制的诊断详情。输入、校验、预览、局部展开和提交反馈均在既有导入区域完成，不新增串行必经页面；文件选择及返回仍计入三步路径。

## 9. 提交以后怎样执行

1. 数据提交后，目标服务和任务服务各通知一次，各页面按真实记录刷新。
2. 现有 PlannedMissionScheduler 重读新排期，AppNotificationService 按当前用户偏好对账。
3. FIXED 仅在开始时刻 ≤ now < 开始时刻+计划时长的窗口内自动写 START；延迟使用真实时刻。整段错过仍待开始。
4. 已有 RUNNING 不被替换；后续释放执行资源且仍在时段内时可以开始，否则手动处理。
5. 达到计划时长只提示；用户报告完成或未完成才产生 END。之后照常走材料及历史流程。
6. 调度/通知失败不回滚已经导入的数据，给出“已导入、提醒待重试”，不能让用户重新创建整包。

Android 的后台路径已有实现，但仍需目标设备验证。Windows / Web 在应用能执行时调度，退出后或浏览器关闭时不能承诺准点开始。导入协议不会改变平台能力边界。
