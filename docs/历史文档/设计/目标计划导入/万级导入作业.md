# 单 Goal 一万任务的导入作业

状态：2026-10-27 设计稿。用户明确单 Goal 约 1 万个任务，本文把[资源预算](容错与大数据量.md)落实为可实施的处理过程；不是当前已存在的导入器。

## 1. 方案选择

正式格式仍是一个普通 goal-package JSON。用户不需要生成 NDJSON、拆成十个目标或手工管理数据库；复杂度由应用处理：

~~~text
文件（≤32 MiB）/ 小文本（≤2 MiB）
    ↓ 64 KiB 分块，原生后台解析 / Web Worker
严格 token 解析 + 有界单对象
    ↓
独立暂存库：原始有效字段 + 规范化记录 + 索引
    ↓ 完整校验、摘要、封存
分页预览：每页约 50 条
    ↓ 用户确认
业务库外层单事务：每批 ≤100 条且 ≤1 MiB
    ↓ 最终检查、回执、COMMIT
页面/调度器读正式记录
~~~

batch 大小是内存与 SQL 驱动策略；全部批次仍在同一个业务事务内。不会出现前 1000 条已在今天页可见、后 9000 条失败的半个 Goal。

## 2. 两种存储各负其责

| 存储 | 内容 | 什么时候可被业务读取 |
| --- | --- | --- |
| 暂存库/工作目录 | 导入作业、已校验输入、规范化行、错误索引、分页数据 | 永不被业务页面/调度器当作正式 Mission |
| 正式业务库 | 现有五类创建记录和 ImportReceipt | 整包 COMMIT 之后 |

原生可用独立临时 SQLite；Web 用 Worker 内有界处理配合 IndexedDB / OPFS 暂存。具体依赖在实施时核对锁定版本能力；不能用全量 Dart List 冒充磁盘暂存。

暂存工作目录由应用生成随机作业 id，使用固定文件名，不接受外部路径。每个作业限制源文件和派生数据总量，建议最多 256 MiB；同一应用库同时只允许一个活跃导入作业，防止叠加分配。临时空间建议预留至少 4 倍文件上限，并覆盖暂存数据库日志；这不是正式数据库/WAL空间估算，平台空间不足仍需可靠失败。

## 3. 暂存记录的最小用途

| 记录 | 必要内容 |
| --- | --- |
| job | 作业 id、状态、协议、已读字节、数量、源摘要、封存摘要、错误概要 |
| goal_input | 原始可用字段、包默认值和 packageId |
| node_input | key 唯一、父 key/根标识、同级顺序、原始可用字段、新 UUID |
| mission_input | key 唯一、输入顺序、nodeKey、原始可用字段、新 UUID |
| resolved_mission | 有效策略、UTC 排期、完整方案、有界行内容及校验结果 |

key 唯一索引在读入时就防重复。nodeKey 在整份文件读完后统一解析，允许根对象字段顺序任意；不能要求 nodes 必须出现在 missions 前面。父节点关系来自 JSON 结构，不接受外部 ID。

原始可用字段只在作业中为规范化摘要和重试保留；作业清理后不在业务表保存原始 JSON。为 JCS 重建需要保留“字段省略”与“显式空数组”等区别，不能先丢弃再假装能算原载荷摘要。

## 4. 有界校验怎样完成

1. tokenizer 在分配大结构前执行深度、值数量、字符串码点及重复对象键检查。
2. 每次只读一条任务；单任务紧凑 JSON 限 256 KiB。保存到暂存后释放正文，不能累积 1 万条内存 DTO。
3. 节点元数据最多 500，可保留小型身份映射；长 description 仍从暂存按需读取。
4. 文件结束后核对根字段、默认值、全部引用、节点数量、任务数量及总步骤。
5. 按源任务顺序逐条展开有效配置、校验统一领域规则并生成规范化行。错误列表有界，错误计数和路径存储可分页。
6. 计划冲突使用排序索引或外部排序，摘要不枚举全部两两组合；候选区间和已有库比较也分页处理。
7. 没有错误后封存，不再允许任意 UI 回调改变已确认行；修改草稿要派生新版本并重新校验。

## 5. 内容摘要不需要整包常驻内存

协议使用 JCS；实现可以从暂存按规范对象键顺序输出规范字节到增量 SHA-256：

- 根字段按规范顺序输出；missions 依源数组顺序逐项读取。
- 每个小对象进行规范序列化；节点树按同级顺序流式遍历，最大递归深度 12。
- 维持字符串和字段存在性的原始语义，不擅自进行 Unicode 归一化或把不同字符串合并。
- 使用符合标准的序列化逻辑和测试向量，不把“按数据库查询顺序拼字符串”当作 JCS。

最终记录载荷摘要，以及将要落库的规范化结果摘要。提交时确认封存版本未变；若时区库/规则更新使规范化结果改变，需要重新生成预览。

## 6. 单事务能否用于一万条

一万任务约三万条创建记录，采用有界 batch 和必要索引后有现实可行性，但必须用实际 Drift、文件 SQLite 与设备测量。不能以 Python 内存数组或原生 SQLite 一条 INSERT 的速度替代整个流程。

事务开始前已完成全部静态校验；事务中重验可变业务事实和时间门槛，不重新跑 UI、文件解码或 AI。捕获创建时刻后按批次写入，最后再检查截止/立即开始边界，全部成功才 COMMIT。

目标写锁时长建议以设备 P95 不超过 2 秒作为首轮评估目标，**不是本轮已经通过的指标，也不是超过后就强杀事务**。若设备实测不达标，先优化批量方式、索引和查询，并检查对到点任务的影响；不得偷偷改成多次可见提交。

若持续无法达到可接受锁等待，需要另审“未发布批次”方案，统一所有读写与后台查询的可见性过滤。它是更大的架构选择，不能只为绕过慢事务就临时加状态。

## 7. 作业状态与崩溃恢复

~~~text
READING → VALIDATING → READY → COMMITTING
   └失败/取消──┴────────┘          ↓
                           以业务回执判定
                         COMMITTED / 可重试
~~~

这些状态是导入技术作业，不是 MissionPhase。

| 重开时看到的状态 | 恢复动作 |
| --- | --- |
| READING 未完成 | 清理或重新读取来源，不把字节偏移当作完整 JSON 断点 |
| VALIDATING 未完成 | 保留可靠暂存输入后重跑验证；无法证明完整则重读 |
| READY 且摘要完整 | 可以恢复分页预览，提交前重查当前业务条件 |
| COMMITTING 且业务回执存在 | 已成功，直接返回原目标，清理暂存 |
| COMMITTING 且回执不存在 | 等业务库正常打开并完成日志恢复后，按未提交处理，可重试原请求 |
| 暂存损坏/版本未知 | 不写正式库，重新读取输入 |

不能以暂存中的 COMMITTED 标记替代业务回执；它可能在正式 COMMIT 后来不及更新。

## 8. 清理和用户操作

当前会话活跃作业不能被另一个实例启动清理。工作目录持有作业租约/锁，只有明确终止或确认没有活跃持有者的作业才清理；不靠“文件看起来旧”就删除。

取消、过期和启动恢复清理都限制在本作业目录；不触碰正式附件。若暂存文件不可删除，只报告临时空间占用并保留清理重试，不回滚已经成功的目标。

长期 READY 草稿需要明确保留时间和用户可见的“继续/丢弃”入口，不能无限堆积占满磁盘。首版可建议保留 24 小时，实施时与本机存储预算一起定稿；未确认的保留时间不能写成已有产品事实。
