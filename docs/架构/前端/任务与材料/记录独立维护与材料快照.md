# 记录独立维护与材料快照

> 2026-11-06：记录用于独立留下内容；关联任务时保存任务材料快照，并由任务结束总结分析。本文描述当前 v16 结构；设备验收单独记录。

## 产品边界

记录可独立存在，也可关联目标、节点；记录本身不生成 AI 摘要。任务材料是任务的一次提交事实，不接管来源记录。任务执行页可在执行中打开当前任务的记录列表；保存记录时同时提交到该任务，形成不可随来源修改的材料快照。

一条记录支持文字，或一个图片/文件附件及说明。多附件编辑和多任务复用不在本轮范围；同一条记录仍最多关联一个任务，但它自己的内容、归属和删除不再因此锁定。

## 数据与职责

| 对象 | 事实和职责 |
| --- | --- |
| Records | 当前内容、来源、发生/保存时间，以及自己的 goalId / goalNodeId |
| EvidenceRecords | 提交时的完整内容快照、提交时间、任务身份和修正链 |
| record_id | 材料来源的稳定编号；可保留已删除来源的编号，不再是强制外键。只改说明的附件修正沿用原件、不新建来源记录，此列为空 |
| ContentDraft | 记录与材料实际共用的内容字段，不含归属、任务和修正身份 |
| RecordDraft | 独立记录保存意图，不包含 supersedesEvidenceId |
| AttachmentCoordinator | 记录和任务共享的附件准备、引用校验、草稿清理与提交互斥 |
| EvidenceDraft / Evidence | 材料草稿、提交快照及追加修正身份 |
| SavedRecord / RecordPage | 页面使用的类型化只读投影；SQL 列名和工具 JSON 留在边界 |

记录修改后，任务材料仍展示当时的快照。记录删除后，材料来源提示已删除，但正文、附件和任务详情继续可读。更新任务材料走已有修正命令，追加历史，不自动跟随原记录。

附件修正有两条路径，都由同一修正命令保存：只改说明时草稿沿用原附件键，`insertEvidence` 以 sharedAttachment 跳过新建来源记录，避免与 records.attachment_storage_key 的唯一约束冲突；更换文件时新附件有自己的键与来源记录。修正草稿沿用原件时，丢弃草稿不会删除原件——协调器只清理"本次新准备且未被任何已提交事实引用"的键。

附件文件不复制；记录与材料快照可以引用同一存储键。清理与备份继续使用两表引用并集，材料仍引用的文件不能被清理。撤销归档中的附件键由 SQL 内的 json_each / json_extract 直接提取，不把整份归档（含全部事件与记录）搬进 Dart 再解码。

附件准备有两道独立上限：字节不超过 20 MiB，像素不超过 4000 万（与助手图片同口径）。字节上限拦不住小体积超大尺寸 PNG，因此先读首帧信息按像素拒绝；image 包自身对超大尺寸抛出的异常同样转成明确的用户提示，不交给平台按原始分辨率解码。写入使用 exclusive 创建，失败只回收本次副本；数据库引用在写入返回之后才保存，因此半截副本不会被任何事实引用。

App 启动即调用一次 AttachmentCoordinator.initialize 回收无引用原件，崩溃或取消留下的副本不必等用户下次打开编辑器才清理；该调用与提交互斥、只执行一次，失败只记录不影响启动。助手会话附件随消息内联持久化，不在附件目录中，因此不受该清理影响。

## 已有调用链

```text
记录编辑器 / 助手保存记录
  → RecordService → AttachmentCoordinator（准备、读取、清理）
  → RecordService.save → 同一附件提交互斥 → 记录仓储事务
    → Records
    → 可选委托统一材料命令 → EvidenceRecords 内容快照

设置记录归属
  → RecordService.setOwnership → RecordRepository.updateOwnership
    → 只更新 Records 的目标、节点

用作任务材料
  → 选择任务 → 预览并确认
  → RecordService.useAsMaterial → MissionService.useRecordAsMaterial
    → 材料事务取得写锁 → 确认已有提交 / 重读并校验预览内容
    → 原子保存材料快照 → 通知重读

任务执行中添加记录
  → MissionExecutionPage 的 RecordsEntry(missionId)
  → RecordsPage / RecordEditor → RecordService.save(missionId)
  → 记录保存与任务材料快照在同一材料命令中提交
  → END 提交后 AnalysisScope.mission 读取有效材料

执行报告 / 实际时间更正
  → 任务模块 ExecutionReportButton → MissionService.reportExecution
    → 既有执行报告和事件事务
```

记录编辑器只使用 RecordDraft 和 RecordService；记录与任务通过同一个 AttachmentCoordinator 协调共享文件。RecordService 与 MissionService 协作提交任务材料并通知事实刷新；执行报告由任务服务处理。

助手使用 setRecordOwnership 设置记录归属，使用 useRecordAsMaterial 提交任务材料；两者分别由业务服务处理，并在事务内保存操作回执供结果恢复。

## 读取与总结

- 记录列表、详情、当日条带和助手共用 SavedRecord / RecordPage；仓储提供类型化摘要和分页，助手入口将其转成有界 JSON。
- 正文展示保留分页；进入文字编辑前单独读取完整正文，保存时进行乐观冲突检查，避免截断长正文。
- 任务详情和助手材料读取均直接读取材料快照，不回退到当前记录内容。
- 任务评价在 END 后排队，输入为任务事实和有效材料快照；任务未结束时材料写入不触发 AI。结束后的补交、修正或任务事实变化会重排任务总结。图片按快照附件逐项观察后汇总，原记录修改或删除不改写评价依据。
- 节点总结只读取直接任务总结和子节点总结；目标总结只读取未归入节点的直接任务总结和根节点总结。直接关联节点/目标的记录仍可浏览，不将原始记录内容或独立记录摘要加入 AI 上下文。
- 来源存续状态只用于导航与提示，不作为读取材料内容的前提。

## 当前开发结构

数据库只维护当前 v16 结构。`onCreate` 创建表、索引并安装当前分析触发器；普通 `beforeOpen` 只设置连接约束，不反复删除/创建触发器，也不改写后台队列。已停用的 record 级待办可留在当前数据库但不会被领取；不新增字段、表或历史数据库适配层。表定义与生成代码是结构来源，测试直接验证当前建库结构与实际约束，不额外保存 JSON 结构副本。

材料 CHECK 要求完整快照，不能用非空 record_id 绕过内容完整性校验。材料附件键允许复用，以便多个修正版本共享文件；来源编号仍唯一，维持本轮单任务引用范围。
