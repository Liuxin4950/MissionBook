## R01：通知入口没有固定报告序号

位置：[执行页初始化](../../../lib/presentation/missions/execution/mission_execution_page.dart:75)、[确认报告](../../../lib/presentation/missions/execution/mission_execution_page.dart:310)、[通知页面分派](../../../lib/app_shell.dart:102)。

通知停止经服务成功写 PAUSE 后，外壳传 `openEndConfirm: true`。初始化只设置 `_report = true`，没有像 `_beginReport()` 那样初始化 `_reportSequence` 和冻结的 Focus。选择完成或未完成后，按钮得到可执行回调；`_confirmReport()` 又因序号仍为 null 直接返回。

复现：真实内存 SQLite 创建任务 → START → PAUSE → 按通知使用的构造参数打开执行页 → 选择完成 → 确认。最终数据库仍只有 START/PAUSE，阶段 PAUSED，没有 END，也没有错误提示。现有“通知服务晚于外壳挂载”测试只验证打开执行页和 PAUSE，未走到报告确认。

修复方向：通知入口与页面内打开报告共用完整初始化过程；以停止后读到的快照固定报告序号。补上通知停止 → 报告确认 → END/必要 FailureRecord 的持久化断言。不要用随意补一个默认序号绕过事务前置条件。

依据：《界面与交互》§7、《领域模型》§9.2。

## R02：自动刷新替旧草稿更换前置条件

位置：[执行页前台恢复](../../../lib/presentation/missions/execution/mission_execution_page.dart:128)、[报告刷新逻辑](../../../lib/presentation/missions/execution/mission_execution_page.dart:197)。

`_refresh()` 的 `acceptReportSequence` 默认为 true。任务变更通知刻意传 false，但回前台调用使用默认值。若旧报告打开后，别的入口让任务 RESUME 再 PAUSE，回前台会把旧报告序号改成最新序号；`MissionActionController.refresh()` 同时清掉 stale。数据库看到的于是成为一个“新鲜”命令，无法再识别这是旧草稿。

复现：序号 2 的 PAUSE 上打开报告并选择未完成 → 其他入口保存 RESUME/PAUSE，序号变 4 → 按合法生命周期转移隐藏再恢复 → 原报告点确认。实际追加序号 5 的 END，而正常预期是保持暂停并要求明确处理旧报告。

修复方向：自动同步事实与用户明确接纳新报告上下文分别处理。生命周期、广播重读不能默默更新已经打开报告的序号；若用户明确刷新后允许继续，也要有清晰的重新确认边界。保留草稿和原序号，让仓储继续执行旧命令拒绝规则。

依据：《领域模型》§9.1、§9.2；《界面与交互》§7。仓储旧序号检查本身没有被此次探针绕过，缺陷发生在 UI 提交前悄悄改变命令输入。

## R03：导航防重入范围仍不一致

位置：[目标新建和选择](../../../lib/presentation/goals/list/goals_page.dart:148)、[今天待补记录](../../../lib/presentation/today/today_page.dart:314)、[节点任务入口](../../../lib/presentation/goals/outline/goal_missions_section.dart:52)。

目标新建设置 `_opening = true` 后等待路由关闭；目标选择又读取同一个锁。今天待补材料的 `_isOpeningRecord` 也锁到路由关闭。这两个左栏在宽屏下仍可见、可点击，但点击被直接忽略。

真实 AppShell 的两个复现已确认：

1. 1280 宽进入目标 → 新建目标（空表单）→ 点击左侧已有目标。没有进入 GoalDetailPage。
2. 两个已结束且待补材料的任务 → 今天左栏依次点击两条待补入口。右栏仍为第一条任务的 MissionRecordPage。

节点任务区源码也存在同样的长时间锁，且会把同一区域的其他任务按钮禁用；此点未另做设备路径复现，不把它算作第三个独立自动验证。

修复方向：工作区外侧的入口复用 DetailPaneController 的“确认离开及派发导航期间”防重入；单独页面或被遮住的内部导航保留适用的防连点。切换仍必须经过草稿守卫，不能简单删掉全部锁。

## R04：刷新目标详情会销毁节点状态

位置：[目标详情 FutureBuilder](../../../lib/presentation/goals/detail/goal_detail_page.dart:134)。

该页面订阅所有 GoalService 变化。只要新查询尚未 done，就返回整块加载圈，即使 FutureBuilder 已保留上一份有效目标，也完全移除正文。其下节点展开、任务展开等 State 随之销毁；读取完成再建一份。修改节点、状态或无关目标均可能触发。

探针用真实目标和受控查询延迟，发出一次无关目标创建通知，确认刷新前后 GoalOutlineSection 的 State 不是同一对象。它与“内容更新”是不同的生命周期结果。

修复方向：同一目标保留最近成功快照及子树身份；首次加载和换目标才替换整个内容，刷新失败在旧内容上提示。后续要覆盖节点/任务展开、窄宽切换和失败恢复。

## R05：隐藏历史页读全量原图

位置：[常驻四主页面](../../../lib/app_shell.dart:171)、[历史分组卡片构建](../../../lib/presentation/missions/history/mission_history_page.dart:229)、[原图 Future 缓存](../../../lib/presentation/missions/history/mission_history_page.dart:415)。

IndexedStack 保留页面本身是合理的；问题是历史页在构造所有分组卡片时就调用 `_thumbnail()`。该方法立即安排初始化和 `readEvidenceImage()`，不等卡片可见；Future 及读出的原始字节留在 `_thumbnails` 中，没有容量或淘汰策略。

探针创建 20 条带正式图片的历史记录，只挂载默认选中今天的 AppShell，没有打开历史页或滚动。存储读取计数已为 20/20。

ResizeImage 控制了解码后的缩略位图尺寸，但不缩小已经读取并缓存的原始文件字节。每项最多三图只限制单条卡片，不限制历史总量。大附件/长期记录会放大启动 IO 和内存占用；本轮没有测量目标设备峰值内存或复现 OOM，不能给出具体崩溃阈值。

修复方向：让图片读取与实际可见项/活跃页关联；改为按需构建卡片，并给原始字节缓存明确边界。保留原文件与放大阅读能力，不能通过丢弃正式附件“优化”。

## R06：查询和调度随历史规模放大

位置：[全量详情循环](../../../lib/data/repositories/drift_mission_repository.dart:795)、[单项详情](../../../lib/data/repositories/drift_mission_repository.dart:1035)、[自动开始全量读取](../../../lib/data/repositories/drift_mission_repository.dart:572)、[前台调度](../../../lib/application/missions/planned_mission_scheduler.dart:54)、[通知全量对账](../../../lib/application/notifications/app_notification_service.dart:119)。

`findAllDetails()` 先查任务，再对每个任务顺序调用 `findDetail()`。独立任务每项额外查询组合行、事件、失败和材料；有关联的任务还会重复读目标及全部节点。`findForGoal()`、历史和当天查询也复用逐项读取。

真实 Drift/SQLite 查询拦截测得：

| 独立任务数量 | 一次仓储 findAllDetails 的 SELECT 数 | 本次宿主内存库耗时 |
| --- | --- | --- |
| 10 | 41 | 22 ms |
| 100 | 401 | 144 ms |

耗时是这次测试宿主的数据，不能当作 Android/Windows 的性能指标；查询数量揭示了确定的放大关系。`EXPLAIN QUERY PLAN` 对详情实际使用的材料查询输出 `SCAN evidence_records` 和 `USE TEMP B-TREE FOR ORDER BY`，不是按 mission_id 定位。材料越多，每项重复扫描的成本越大。

调度器在写事务内执行到点处理时先读全量详情，之后又为下一唤醒读全量详情；通知对账再读全量。多个页面和服务订阅同一无内容变更流，还会重复发起各自查询。没有按一次完整变更测总 SQL，不把上述局部计数冒充完整事件成本。

修复方向：先保留同一快照和唯一阶段规则，按候选任务筛选自动开始、批量装配相关事实，补材料查询索引并包含旧库迁移验证；再合并重复查询。不能新增可写 phase 或跨事务沿用旧缓存来省校验。

## R07：父组件重建引起无意义数据重读

位置：[目标记录摘要 didUpdateWidget](../../../lib/presentation/goals/shared/goal_record_summary.dart:55)、[节点工作区 didUpdateWidget](../../../lib/presentation/goals/outline/goal_outline_section.dart:100)。

目标摘要在服务、目标编号均未变化的 else 分支仍执行 `_read()`。纯粹切换选中样式、窗口布局或父组件 setState 也会再次读节点、查询任务，并经 MissionService 做截止补算。节点工作区也有相同的无条件重读分支。

最小 Widget 探针保持所有输入与数据库不变，只重建父组件一次；空目标额外执行 3 次 SELECT。数据量更大或多卡片时还会叠加 R06。

修复方向：区分配置变化、事实变化和普通绘制。保留初始化、服务通知及明确返回/核对结果的刷新入口；响应丢失后的核查仍要接通，不能为消除查询直接删掉必要恢复路径。

## R08：备份把慢 IO 和数据库操作绑在一起

位置：[备份事务](../../../lib/data/backup/database_backup_service.dart:17)、[事务内附件读取](../../../lib/data/backup/database_backup_service.dart:59)、[内存归档压缩](../../../lib/data/backup/database_backup_service.dart:84)。

备份在数据库事务中导出全部表后，继续逐个等待正式附件读取。应用复用同一数据库连接，其他操作要等这个事务结束。探针阻塞一个附件读取，同时取消另一个待开始任务：附件未释放时取消尚未返回，释放附件后才保存 CANCELLED。这里验证的是连接队列等待，不等于已经测到 UI 掉帧。

此外，全部 SQL 和原始附件组成内存 Map，交给压缩函数后再整体返回 ZIP；没有流式输出和总量边界。附件数量没有因“每个最多 20 MiB”而受到限制。这是可见的内存增长风险，未测设备内存峰值。

修复方向：在一致事务里固定数据库快照和正式引用清单后尽早释放连接；正式附件不可变的约束允许据该清单继续归档。采用有界中间存储/流式压缩时仍要覆盖缺失附件、失败、取消和独立还原验证。

## R09：多服务共享附件存储时的清理竞争

位置：[首次附件初始化](../../../lib/application/missions/mission_service.dart:203)、[删除未引用文件](../../../lib/application/evidence/evidence_image_service.dart:163)。

每个 MissionService 分别缓存 `_imageInitialization`。第二个服务首次进入材料区时，只按正式数据库引用清理整个附件目录，无法识别另一个服务仍在使用的草稿。已有串行队列只保护同一个服务内的提交/删除。

探针让两个真实 MissionService 共用数据库仓储和同一内存文件存储：A 选文件并持有草稿 → B 初始化附件 → A 的副本已被删除。正式记录没有被此探针删除，丢失的是未提交附件副本；下一次提交/阅读会失败。

触发条件是多实例共享同一附件存储，如同源多个预览标签页或实际允许的多窗口。当前规格没有把多标签并发作为正式设备验收承诺，因此单列条件风险，不宣称用户单实例日常操作一定遇到。后续应明确限制多实例，或定义能识别活跃草稿的共享协调/清理边界，不能仅扩大进程内 bool 锁。

## 调用关系与检查边界

正常写入关系保持为：页面/通知提交意图 → MissionService/GoalService → 仓储取得写权限并重读 → Domain 校验 → SQLite 原子提交 → 广播要求相关页面/调度重读。此次问题主要集中在调用入口前置条件、刷新生命周期和查询资源消耗，没有证据要求推翻现有分层或引入新的状态管理框架。

| 检查单元 | 核对内容与结果 |
| --- | --- |
| 任务创建、编辑、取消、RETRY | 核对固定创建请求、未知结果查询、事务前置条件、排期追加、归属与终态；未在本轮新增一条已复现写入缺陷 |
| 执行、报告与全局活动任务 | 核对唯一时间线、序号/身份、PAUSE/END 两提交边界、时长；R01/R02 属于入口和刷新改变前置条件 |
| 首批材料、修正、截止 | 核对整批事务、正式材料追加、超时与提交互斥、草稿离开保护、文件准备；R09 为跨服务清理边界 |
| 目标、节点、导入与覆盖率 | 核对树约束/归档/调序、导入限制/原子保存、直接完成报告口径；发现 R03/R04/R07 |
| 今天、历史、全部任务与个人页 | 核对筛选、返回链、快照、隐藏页面和图片读取；发现 R03/R05/R06，保留此前两处修复 |
| 计划自动开始、通知与生命周期 | 核对冲突保留、真实 START 时刻、动作稳定身份、前后台入口；R01/R02/R06，系统送达仍需设备证据 |
| 资料、权限、备份、迁移 | 核对偏好与领域库分离、权限未知状态、保存出口、一致快照及增量迁移；R08，未操作用户文件 |

没有把以下事项误列为新缺陷：FLEXIBLE 的提前手动开始有现行界面规格依据；文件材料只显示原名/大小符合当前范围，不擅自要求内置文件阅读器；Windows 无法撤销已排提醒的发行形态限制已有说明，仍需平台验收。目标设备通知、相机、跨进程、升级、长列表帧耗和峰值内存没有因测试通过而自动获得验证。
