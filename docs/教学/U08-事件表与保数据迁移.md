## 1. 为什么已有对象，还要定义表

## 2. 同一任务下，数据库保护什么

用任务 A 举例：

- `id` 是事件主键，重复事件编号不能插入第二次。
- `(mission_id, sequence)` 组合唯一：A/1、A/2、B/1可以共存，第二条A/1被拒绝。
- START 和 END 分别使用部分唯一索引：只限制这两类行，每个任务各至多一条。PAUSE、RESUME、EXTEND仍可多次出现。
- 任务和排期外键引用现存记录，不级联删除历史。排期是否属于同一任务、是否最新，仍须事务内查询校验。
- CHECK 限制正序号、正延长分钟、已知动作和报告文本。可空字段的null含义保留；布尔值true、false、null分别读回。

不能把 `(mission_id, type)` 整体设为唯一，否则A的第二次暂停也会被拒绝。部分唯一索引中 `WHERE type = 'START'` 的意思是：只有开始事件参加这项唯一检查。

这些 SQL 约束不推演完整业务过程。例如数据库序号唯一不能判断1后面直接出现3，外键也不能判断任务是否已取消。字段适用条件、序列连续、时间顺序与合法动作仍复用现有领域规则，并在未来统一写事务内读取真实事实后校验。

本轮没有提供修改/删除事件的业务接口，也没有增加不可变触发器；底层连接不是完整业务入口。测试中的直接表写入用于单独检验SQL约束，部分测试故意绕过时间线规则，不可复制成生产执行流程。

## 3. 为什么版本改为2

旧设备已经保存了三张表，仅在源码中声明第四张表，不会使旧设备自动获得它。Drift打开连接时会比较数据库的 `user_version` 和代码的 `schemaVersion`。

```text
首次安装：没有数据库 → 默认 onCreate → 全部四表及索引 → 外键开启 → 普通查询
已有v1：旧三表保留 → onUpgrade(1, 2) → 新事件表及两个索引 → 外键开启 → 普通查询
已有v2：无需迁移 → 外键开启 → 普通查询
```

`onUpgrade` 是交给 Drift 的回调；打开旧库时由 Drift 调用，并传入旧版本和新版本。`migrator` 是它提供的结构修改工具。升级事务内依序执行：

```dart
await migrator.createTable(executionEvents);
await migrator.createIndex(executionEventsOneStart);
await migrator.createIndex(executionEventsOneEnd);
```

这是已有 `AppDatabase.migration` 内的实际代码，不是要额外粘贴的另一段。`createTable` 只建表，独立索引必须另外创建；首次安装默认的 `createAll` 则会一起创建声明过的表和索引。

外层 `transaction` 让三步与 `PRAGMA user_version = 2` 版本标记一起成功或一起回滚。Drift默认在全部开库回调完成后才更新版本；这里让版本和结构同时提交，避免升级已提交、后续开库中断时，重开仍按v1重复创建索引。没有删除/重建旧表，也不为旧任务虚构 START。升级失败将异常交回既有页面错误路径，不会自动删库重试；用户设备恢复提示与实际平台升级体验仍待设备验收。不认识的版本明确报错，不尝试猜测迁移或降级。

## 4. 已验证的结果与边界

修改前先重新导出v1结构，与仓库已保存快照比较一致，原快照保留。测试从该快照创建独立文件旧库，放入未开始与已取消任务、多版本排期、固定/自选时间、描述、步骤和方案，再关闭连接后让真实 AppDatabase 升级。

10项测试覆盖：逐字段保留旧三表、新表初始为空、升级后事件保存与关闭重开、升级结构与新装定义一致、外键有效、主键和组合唯一、START/END部分唯一、基本CHECK、三态布尔值。另故意制造索引名冲突，使创建END索引时失败；确认此前新表/索引全部回滚、版本仍为1、旧数据不变，排除故障后再次升级成功。还模拟升级提交后开库回调抛错，确认再次打开能正常使用v2，不重复升级。

测试只使用专属临时库，没有打开用户的原生或浏览器数据库。未进行Windows/Android实物升级验收，未验证执行操作的幂等或并发。全量自动检查结果见学习进度；下一步接业务对象/数据库行转换与统一事务写入，再落实U09开始、暂停、继续、延长及其与取消/编辑的互斥。
