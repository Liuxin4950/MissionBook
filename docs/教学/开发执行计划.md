# Mission Book 开发执行计划

本轮衔接（2026-10-31）：用户已授权直接实现[记录、补记与分层理解](../设计/记录、补记与分层理解.md)。后续讲解沿现有层次追踪两条完整事实链，不将模型评价当执行事实；实现与设备/学习验收分开。Skills、Python、每日自动规划不进入本轮。

本文是 MissionBook 学习式开发的教学约定：让用户沿真实代码理解设计和调用，并能亲自实现一个完整功能单元。当前版本依据 2026-10-20 的整轮反馈统一修订。

[教纲](教纲.md)负责课程路线，[学习进度](学习进度.md)负责当前实现、验证与理解状态，[变更记录](变更记录.md)负责调整依据。本文定义教学方式，其他入口引用它，不再各自追加不同的输出模板。业务要求以 `docs/需求文档v1.0/` 相关规格和用户最新约束为准。

## 1. 从最终结果反推结构

- 每个新功能先读对应规格、设计规范与现有代码，说明本轮目标、它在完整功能中的位置，以及实际涉及的目录和职责。页面用组件关系定位，数据功能用对象关系或调用链定位。
- 给出实现代码前先展示本轮目录变更，标明新增、修改、仅参考；即便只改一个已有文件，也明确无新增目录或文件。每段代码注明文件、插入或替换位置，以及所属类/函数；说明原有代码保留还是替换。独立调用示例注明由谁、何时使用，不把尚未接通的示例当成当前可直接粘贴运行的代码。
- 已知的布局、导航、安全区域、滚动、主题和业务结构，在首次实现时就安排好；不为教学方便先搭临时结构，随后要求用户返工。
- 定义模型前说明业务依据、字段来源和对象关系，交代本轮覆盖与暂缓范围。当前切片不能冒充完整最终模型，已知省略项不能默默丢掉。
- 只增加当前需要的结构，不提前建立空表、空接口、通用框架或无使用者的文件。保留用户已有改动。
- 目录归类与拆文件分别判断：文件平铺太多、难以找到页面时，按业务功能分文件夹；普通页面组件优先留在页面文件中，不因行数或界面区域数量拆文件。只有状态变量多、交互复杂、独立性很高或有明确复用需要时，才考虑独立组件文件。转换函数大量堆积、遮挡页面主流程时，单独放转换文件，让页面入口和调用顺序先可见；避免为缩短文件造成来回跳转。

## 2. 按完整功能单元推进

- 一个单元应有明确用途和可观察结果，例如一个完整界面区域、一个转换函数或一次事务保存。不要逐行挤出，也不要一次倾倒整页及全部业务代码。
- 实现粒度与解释粒度分别控制：实现保持完整，讲解沿当前因果和调用过程展开，必要时分几轮说明；不能将“渐进式”机械等同于拆代码块。
- 用户反馈太多或不懂时，缩小到当前卡点，保留理解它必需的上下文。不要借此新增下一功能，也不要重新讲已经明确理解的部分。

### 2.1 连贯的渐进式讲解（强制）

用户需要的是能跟上思路的教学：每出现一段代码，都能知道为什么写、接着什么、会得到什么。精简是减少重复和无关内容，不能省略理解所需的前提，也没有固定句数或代码块数量。

1. **从当前业务和真实代码起步。** 先交代本次要解决的具体问题及所在位置，再沿“业务需要 → 结构和字段依据 → 创建或调用过程 → 实际结果 → 后续使用”组织说明。首次讲功能给必要的全貌，后续承接当前卡点，不每轮重讲全套背景。
2. **让代码与思路在同一个位置相接。** 写到某个处理时，就近说明它的目的、参数来源和返回结果；短段落与必要中文注释配合。类或函数顶部用 `///` 简要说明整体用途；具体参数、字段及语句的简短解释写在对应代码行末的 `//` 后，例如 `required this.mission, // 任务本身`，不把成员逐项解释和例子集中堆在顶部，也不在构造参数与字段声明重复相同说明。中文注释要覆盖当前理解需要的新语法和调用，例如构造函数怎样接收数据库、成员变量保存什么、async/await 等待什么、事务回调由谁执行和错误如何传回；不能只写“保存任务”等动作标签，也不逐行重复已理解的内容。注释先帮助用户沿代码理解“这一行定义或调用了什么、值从哪里来、结果交给谁”，再按需说明业务约束。例如 `Stream<void> get changes => _changes.stream;` 应注释“定义一个公开的只读属性，让页面拿到这个控制器提供的事件流”，不能只写“只通知重读，不用通知内容充当数据库事实”而省略 getter 和返回对象的作用。禁止先贴完整实现，再在末尾集中补一篇说明；也不能把长篇说明全部塞进注释当作教学。
3. **保持可见的完整逻辑。** 短函数可以连贯展示并就近解释；较大单元按有意义的职责或步骤展开，必须交代当前片段所属对象、入口和结果去向。不能把函数开头、零散参数和结尾拆成独立代码块，让用户靠拼括号恢复结构。分段由内容决定，不强制整段或强制拆段。
4. **以同一次调用串起值的流动。** 用一个贯穿的具体例子，说清调用者如何提供值、当前代码如何使用、结果由谁接收。区分对象构造、业务校验、数据库保存与页面展示，避免把准备数据讲成已经保存。
5. **按当前理解需要解释。** 新语法、新工具和英文类型在首次影响理解时说明；已知内容不逐行翻译。相关替代写法只在解释当前选择时补充，不为凑全面而穷举。理解检查应自然衔接当前问题，不在解释后突然考问，也不靠强制问答推进课程。
6. **纠正要落实到讲法。** 用户说“重来”或指出问题时，结合其明确反馈重新组织当前过程；不能原样重发、仅更换标题或增加注释，更不能把最近一句反馈放大成新的绝对规则。规则维护要合并既有要求、检查相邻文档，而不是每次追加一个相互冲突的补丁。

发送前自行核对：当前问题是否被回答；上下文和输入到结果是否连贯；解释是否紧邻相关代码；是否省略必要前提或重复已有理解；是否超出本轮范围。检查用于修改答案，不把清单交给用户校准。

## 3. 关键概念怎样解释

- 讲参数时同时说明名称和实参的来源：名称由哪个类或 API 定义，值由用户输入、调用者、系统、框架回调还是我们写定。字符串字面量不会自动查找枚举；构造默认值与数据库默认值也有不同触发时机。
- 初次遇到类、构造函数、命名参数、空安全、枚举、final、const 等语法，结合正在发生的行为解释，不据单个已知概念推断其他语法也已掌握。不要一次展开所有相关知识。
- 链式调用、工厂、回调和辅助函数要追踪输入、返回类型与接收者；讲嵌套类型先说明每层实际装什么，再介绍名称。实现以语义明确、调用可追踪为先：复杂条件用普通 if/else，转换过程用具名中间变量和清晰的循环，不为了压缩行数使用嵌套三元表达式或多层链式简写。保留已经直白的常用语法，不机械展开所有 Dart 写法。
- 模型和表的字段用中文说明业务含义、单位、空值含义与适用条件。必需配置、可选设置、框架默认值各自讲清；有用的替代方案在主过程清楚后简要比较。
- 区分业务对象、数据库表和查询结果，说明转换者与依赖方向。`domain` 定义业务类型、规则和接口，`data` 负责存储与转换并依赖 `domain`；不把 Drift 表放进 `domain`，也不强求业务对象逐表逐字段对应。
- 技术工具先说明当前功能为什么需要、由谁调用、输入与产出、运行时机，再给命令。生成工具须区分源文件、生成代码、运行库与用户数据文件，以及开发电脑和用户设备各自执行的步骤。
- UI 讲解说明组件职责、关键属性和布局关系；主题区分 Flutter 默认、项目统一配置与页面局部设置。抽象关系难懂时使用必要的图与同一个例子，不继续堆术语。

## 4. 一轮怎样承接

先核对源码与学习进度，再根据用户这一轮的目的选择动作，而非每次套用同一篇格式。

| 用户当前需要 | 对应做法 |
| --- | --- |
| 开始或继续一个功能单元 | 交代目标、必要结构和修改位置；按第 2.1 节讲清过程，给出可操作的实现与当前单元的观察结果。自然衔接后续位置，不提前塞入下一单元代码。 |
| 询问概念、看不懂或要求重讲 | 围绕当前调用及缺失的前提解释，保持代码上下文；暂不扩展功能，不强制附带测试、替代方案、复述题和下一课。必要澄清只针对尚不清楚的卡点。 |
| 授权代写、排错或普通实现 | 直接完成授权范围并验证，报告结果及实际边界。结合当前指向判断范围，不能因“写完这个函数”就扩成整个仓储、业务入口或页面。 |
| 要求修改教学规则或文档 | 回看完整反馈，统一入口、详细规则、教纲和当前状态，保留仍然有效的要求；不要只追加局部补充、反复道歉或靠承诺代替文档与行为调整。 |

默认由用户亲自实现，明确授权后由助手实施，无需重复索要确认。授权代写不等于已经理解；讲解、实现和验证应分别记录。

## 5. 设计、图解与返工

- 根据最终规格可以预先确定的结构应首次安排好。确需调整时说明原因、替代方案、影响、保留内容与验证，记录变更并同步相关规格，不能把前期遗漏当成正常教学步骤。
- 架构或流程变化、抽象关系难以理解时给出对应图解，标清已有与规划。用户要求的架构和完整功能图用内置生图；先通过[完整功能图解](完整功能图解.md)定位总图，再按当前课需要提供分支细图。图的文字与箭头先核对，正式图、提示词与制作过程按现有目录归档。
- 页面路径先满足三步原则，系统选择器和必要返回计数；不靠多页实现后再返工。未接通的交互不能用空回调、假数据或临时提示冒充完成。
- 已有反例：今天页后来才改滚动容器和移除导航壳重复顶栏。这些已知要求应在页面骨架设计时确定，后续避免重复。

## 6. 实现、验证与学习的记录

- 按依赖推进，开始下一单元前核对实际实现；示例代码、方案讨论或一个概念讲过都不等于已落地。
- 学习进度分别记录实现、实际验证与用户掌握。没有用户复述或独立操作证据就保持待确认，不能用测试通过代替掌握，也不为填写记录而强迫用户回答问题。
- 设备验收与静态检查、自动测试分开；没有目标平台的实际证据，不宣称平台持久化或交付通过。
- 当前状态只在学习进度维护；教纲链接该状态，历史课和图片快照注明时间。规则反馈合并到适当正文，变更记录保留必要缘由，避免不断追加重复的聊天复盘。

## 8. 本次学习中暴露的问题与纠正方式（2026-10-19）

以下记录是已经发生的教学问题，供后续开讲前核对；不能仅以“会更详细”或“会更简洁”代替纠正。

| 遇到的问题 | 造成理解困难的原因 | 后续必须采用的讲法 |
| --- | --- | --- |
| 分不清 domain 对象与 data 表定义 | 先讲目录、依赖等抽象术语，没有先说明同一任务的两种表达及转换者 | 用同一条任务说明：业务对象表达业务，表定义表达存储；data 仓储负责转换，domain 不引用 data 表。简单场景可以一一对应，不把额外拆分说成必需。 |
| 英文字段看不懂 | 给了大量字段名，注释没有覆盖实际业务含义 | 在字段旁给中文解释，例如计划分钟数、记录产生时刻、所属任务编号；不要只翻译词语而遗漏单位和空值条件。 |
| 构造函数的 `({ ... })` 被理解为两层嵌套 | 没有区分参数列表与命名参数的括号职责 | 就当前括号解释：圆括号是参数列表，花括号标记命名参数；配一个带参数名的实际调用。不要同时引入继承和代码生成。 |
| 不知道 `'SELF_REPORT'` 是从哪里找到的 | 没有区分字符串字面量、业务枚举与转换代码 | 说明该文本是我们依据规范写定的存储值；它不会自动查找枚举，data 负责显式转换。再区分构造默认值和数据库列默认值各自在何时生效。 |
| 不理解 `List<Set<Column>>` | 只给泛型结构，没有先指出元素是列定义而非记录值 | 用一组 `{missionId, revisionNumber}` 说明两列组合唯一，再用 A/1、A/2、B/1 举例；外层列表允许多组约束，内层集合选取一组列。不能把 Set 说成自动清理数据库重复行。 |
| 不知道 build_runner、生成 Dart 文件、SQLite 分别是什么 | 工具命令先于用途说明，混在一起讲开发时和运行时 | 先对准“保存任务后重开仍在”：SQLite 运行库负责读写数据文件，Drift 组织 Dart 数据访问；build_runner 在开发时启动生成器，生成配套 Dart 代码，用户设备不运行生成命令。 |
| `extends _$AppDatabase` 报错后无法继续 | 初次说明没有让生成步骤和入口必需配置形成可执行的修复过程 | 检查 part 声明、父类生成情况和入口内容，读取生成输出，再验证静态检查。不能仅凭错误提示猜测，也不能以手写生成类绕过。 |
| AppDatabase 构造函数仍看不懂 | 把继承、连接类型、可空参数、配置对象、目录函数和测试注入一起展开 | 从 `AppDatabase()` 开始，只跟踪 executor 为 null → driftDatabase 按我们提供的配置准备连接 → 连接传给 super。参数名由库定义，名字和配置值由我们填，目录由系统函数取得。测试连接作为主过程讲通后的补充。 |
| 看不懂 schemaVersion、migration、beforeOpen | 逐个介绍语法和术语，没有说明读取者、调用者与触发时机 | 沿开库顺序解释：Drift 读取版本和策略，按需建表或迁移，调用我们提供的 beforeOpen 函数，等待外键开启，再执行普通操作；details 由 Drift 传入。属性配置、回调函数和立即执行的操作分开说明。 |
| 多次“详细解释”仍然过载 | 用更多章节和 API 解释回应困惑，没有针对真正卡住的值传递过程；一度又退回用户已理解的继承 | 详细指把当前一条过程讲清楚，不代表覆盖所有相关知识。以用户点出的代码为边界，先给用途，再跟踪一次调用；问题讲通后才补必要语法，不扩展新的功能代码。 |

有效示例：用户问“如何连接、参数哪里来”，直接回答“调用 AppDatabase() 没传 executor，所以为 null；采用右侧 driftDatabase，根据我们填写的文件名和目录配置准备连接，最后传给 super”。这比同时展开整个类的所有语法更容易衔接。

下次接续教学前的内部检查：当前要实现什么；用户究竟卡在哪里；每个关键值由谁提供、流向哪里；解释中是否混入多个独立概念；代码落地和用户理解分别到了哪一步。检查结果用于调整回答，不让用户承担反复提醒的责任。
