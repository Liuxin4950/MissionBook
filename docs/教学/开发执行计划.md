# Mission Book 开发执行计划

本文约束后续的学习式开发：依据最终产品规格反推结构，再按完整功能单元逐步教学，帮助用户理解 Flutter 的组件、布局、主题与业务实现。

逐课路线、每步理由与验收见[学习开发教纲](教纲.md)；持续更新的当前进度见[学习进度](学习进度.md)；课程与设计变化见[变更记录](变更记录.md)。本文保留教学原则和既有复盘，第 7 节是建立教纲时的历史检查点，后续进度不在两处重复维护。

## 1. 从最终结果反推

- 每个功能开始前，先阅读对应产品规格、设计规范和现有代码，明确最终布局、交互与数据职责。
- 先展示目标组件树和必要的目录变化，说明每个组件、文件负责什么，再开始写代码。
- 预先确定已知的结构要求，例如页面与导航壳的分工、安全区域、滚动方式、统一边距和主题归属。
- 后续步骤应在已确定的结构内增加内容，避免为了教学方便先写临时结构，随后再要求用户替换。
- 最终结构只覆盖当前规格，不为未来能力提前增加空接口、额外分层或未使用文件。
- 定义模型前，先说明字段来自哪些业务要求、对象之间如何关联，以及本轮覆盖和暂缓的范围。部分切片不能被称为完整最终模型；已知的省略项与后续接入方式须提前交代。

## 2. 按完整功能单元教学

- 一次完成一个能够理解、运行和观察结果的单元，例如“顶部布局与内容”或“日程标题与空状态”。
- 不把一个完整思路拆成“一次只增加一个 Text、Row 或属性”；也不一次交付整个页面及全部业务代码。
- 保持上下文连贯：说明这一步承接什么、完成什么、后续内容接在哪里。
- 用户反馈内容过多时，缩小功能范围，但保留该单元的完整结构和解释；不要退化成逐行挤出代码。
- 区分实现粒度与解释粒度：代码按完整功能单元组织，解释可以分几轮沿一条实际调用逐步展开。完整不等于一次讲完所有概念；精简也不等于跳过当前问题所需的前提。
- 用户说“看不懂、太多”时，立即停止推进，重新定位其当前问题，只解释对应的调用或数据关系。不要把同一篇长解释换成更多小标题重讲，也不要退回用户已经明确理解的部分。

## 3. 解释选择与常见替代写法

- 给代码时，解释组件和关键属性的作用、为什么适合当前需求，以及省略后的默认行为。
- 对存在常见选择的地方，简要比较一到两种替代写法，再明确本次推荐及理由；不穷举所有 API，也不把一种写法说成唯一正确写法。
- 区分实现所必需的设置、设计效果所需的可选设置，以及框架或主题已经提供的默认设置，避免无理由重复配置。
- 遇到链式调用、工厂或辅助方法时，说明值从哪里来、返回什么类型、最终由哪个属性接收。
- 解释调用过程时，从一次实际调用出发，沿着“谁传参数 → 参数取什么值 → 调用谁 → 结果交给谁”讲解；不要把继承、代码生成、连接和回调等多个概念同时展开。用户反馈过多时，缩小到当前卡住的过程。
- 遇到主题时，区分 Flutter 默认值、项目统一配置和页面局部修改；说明修改是否影响全局，避免页面反复覆盖本应统一的样式。
- 解释放在相关代码附近，使用必要的注释和短段落，不把简单功能变成大篇幅 API 手册。
- 解释必须串成完整过程：为什么需要这个对象或组件 → 字段和参数从哪里来 → 怎样创建或调用 → 得到什么结果 → 后续谁使用。不能仅罗列语法含义，或用“后面再说”跳过理解当前代码所需的前提。
- 初次出现类、构造函数、命名参数、空安全、枚举、final、const 等概念时，结合当前代码说明具体行为、选择理由和常见替代写法；不因用户已经理解某一概念，就假设其掌握所有 Dart 语法。
- 模型和表的字段必须有中文注释，交代业务含义、单位、空值含义及适用条件；关键英文类型、参数和工具首次出现时给中文用途，不要求用户靠英文名称猜作用。
- 讲参数时，明确参数名由哪个 API 定义、实参值由谁提供：用户输入、我们写定、调用者传入、系统返回或框架回调。字符串常量与枚举映射、默认值与自动查找不能混为一谈。
- 讲嵌套类型时，先说每层实际装什么，再讲类型名称。例如 uniqueKeys 外层是多组约束，内层是一组列定义；Set 的元素去重与数据库记录的 UNIQUE 检查是两件事。
- 替代写法用于回答当前选择疑问，推荐方案的主过程讲通后再简要补充；不要为了“全面”把不同方案、测试入口和多个新概念一起塞进主解释。
- 代码配一个必要的完整调用过程，明确对象创建、业务校验、数据库保存、页面展示分别在哪一步发生，避免把“能构造对象”讲成“数据合法或已持久化”。
- 解释分层时，区分业务对象、数据库表和查询展示结果，直接说明依赖方向、转换由谁完成；不能把目录命名讲成语言强制规则，也不能暗示业务对象必须逐表逐字段对应数据库。
- 用户反馈抽象解释难以理解时，优先用一张简洁关系图配具体例子说明，不继续堆叠术语和长段落。

例如：顶部先说明 `Row → Expanded → Column + 按钮` 的空间关系，再解释 `Expanded` 与 `spaceBetween` 的取舍；使用 `styleFrom` 或 `copyWith` 时，解释它们生成的样式对象及适用场景。

## 4. 每轮教学流程

1. 检查当前代码，确认用户已经完成的部分，避免重复要求修改。
2. 给出本轮目标、最终组件结构和目录变化，只列实际涉及的少量文件。
3. 说明组件与写法的选择依据，然后给出代码，并明确新增、替换或保留的位置。
4. 提供可观察的验收结果，例如热重载后应看到什么、点击后应发生什么。
5. 简要交代下一单元与当前结构的衔接，不提前塞入下一单元的代码。

默认提供代码与指导，让用户亲自实现；用户明确要求代为修改时，再直接修改实现文件。用户提出概念问题时，先把当前问题讲清楚，不同时推进新的功能。

每轮教学开始前，内部核对以上规则是否落实，尤其检查完整思路、必要前提、范围边界和后续衔接。不要反复向用户宣读规则，也不要等用户再次提醒才补解释。

技术工具第一次接入时，先用当前功能说明“为什么需要、谁调用、输入是什么、产出是什么、何时运行”，再给代码和命令。涉及生成工具时，明确源文件、生成代码、运行库、运行时数据文件的区别，以及开发电脑与用户设备分别执行哪些步骤。

用户授权接手排错时，检查当前文件、依赖和命令输出，完成修复及针对性验证；不要只重复“这是正常红线，执行生成即可”。修复后先说明实际补了什么、已验证到哪里，再按用户当前卡点解释。接手实现不代表用户已经理解，不因测试通过而自动推进下一功能。

## 5. 避免不必要的返工

- 不用空回调、假业务数据或临时提示冒充已实现的功能；尚未接通的交互应明确标识。
- 能根据最终规格确定的容器和职责，在该功能第一次教学时就确定，不留到后面反复改写。
- 确实需要调整既有结构时，说明具体原因、影响范围和保留部分，区分新增需求、实际约束与前期设计遗漏。
- 不承诺永远不调整，但不能把可预见的结构遗漏当成正常教学步骤。

已发生的反例：今天页先使用最外层 `Column`，后续才根据早已存在的页面需求改为滚动容器，并删除导航壳中的重复顶栏。这些要求应在页面骨架设计时统一考虑，后续教学避免重复此过程。

## 6. 任务粒度与进度

- 按“页面骨架 → 完整界面区域 → 真实数据与业务交互”的依赖顺序推进；功能顺序仍须结合当前规格确定。
- 进度以现有代码和实际验收为准，明确区分静态布局完成、交互接通、数据持久化和运行验证。
- 示例代码、方案讨论或用户理解概念，不自动代表代码已经落地或功能已经验收。
- 开始下一单元前核对实际实现，不因教学节奏反复更换已确定的结构。

## 8. 本次学习中暴露的问题与纠正方式（2026-10-19）

以下记录是已经发生的教学问题，供后续开讲前核对；不能仅以“会更详细”或“会更简洁”代替纠正。

| 遇到的问题 | 造成理解困难的原因 | 后续必须采用的讲法 |
| --- | --- | --- |
| 分不清 domain 对象与 data 表定义 | 先讲目录、依赖等抽象术语，没有先说明同一任务的两种表达及转换者 | 用同一条任务说明：业务对象表达业务，表定义表达存储；data 仓储负责转换，domain 不引用 data 表。简单场景可以一一对应，不把额外拆分说成必需。 |
| 英文字段看不懂 | 给了大量字段名，注释没有覆盖实际业务含义 | 在字段旁给中文解释，例如计划分钟数、记录产生时刻、所属任务编号；不要只翻译词语而遗漏单位和空值条件。 |
| 构造函数的 `({ ... })` 被理解为两层嵌套 | 没有区分参数列表与命名参数的括号职责 | 就当前括号解释：圆括号是参数列表，花括号标记命名参数；配一个带参数名的实际调用。不要同时引入继承和代码生成。 |
| 不知道 `'SELF_REPORT'` 是从哪里找到的 | 没有区分字符串字面量、业务枚举与转换代码 | 说明该文本是我们依据规范写定的存储值；它不会自动查找枚举，data 负责显式转换。再区分构造默认值和数据库列默认值各自在何时生效。 |
| 不理解 `List<Set<Column>>` | 只给泛型结构，没有先指出元素是列定义而非记录值 | 用一组 `{missionId, revisionNumber}` 说明两列组合唯一，再用 A/1、A/2、B/1 举例；外层列表允许多组约束，内层集合选取一组列。不能把 Set 说成自动清理数据库重复行。 |
| 不知道 build_runner、生成 Dart 文件、SQLite 分别是什么 | 工具命令先于用途说明，混在一起讲开发时和运行时 | 先对准“保存任务后重开仍在”：SQLite 运行库负责读写数据文件，Drift 组织 Dart 数据访问；build_runner 在开发时启动生成器，生成配套 Dart 代码，用户设备不运行生成命令。 |
| `extends _$AppDatabase` 报错后无法继续 | 初次说明没有让生成步骤和入口必需配置形成可执行的修复过程 | 检查 part 声明、父类生成情况和入口内容，读取生成输出，再验证静态检查。不能仅凭错误提示猜测，也不能以手写生成类绕过。 |
| AppDatabase 构造函数仍看不懂 | 把继承、连接类型、可空参数、配置对象、目录函数和测试注入一起展开 | 从 `AppDatabase()` 开始，只跟踪 executor 为 null → driftDatabase 按我们提供的配置准备连接 → 连接传给 super。参数名由库定义，名字和配置值由我们填，目录由系统函数取得。测试连接作为主过程讲通后的补充。 |
| 看不懂 schemaVersion、migration、beforeOpen | 逐个介绍语法和术语，没有说明读取者、调用者与触发时机 | 沿开库顺序解释：Drift 读取版本和策略，按需建表或迁移，调用我们提供的 beforeOpen 函数，等待外键开启，再执行普通操作；details 由 Drift 传入。属性配置、回调函数和立即执行的操作分开说明。 |
| 多次“详细解释”仍然过载 | 用更多章节和 API 解释回应困惑，没有针对真正卡住的值传递过程；一度又退回用户已理解的继承 | 详细指把当前一条过程讲清楚，不代表覆盖所有相关知识。以用户点出的代码为边界，先给用途，再跟踪一次调用；问题讲通后才补必要语法，不扩展新的功能代码。 |

有效示例：用户问“如何连接、参数哪里来”，直接回答“调用 AppDatabase() 没传 executor，所以为 null；采用右侧 driftDatabase，根据我们填写的文件名和目录配置准备连接，最后传给 super”。这比同时展开整个类的所有语法更容易衔接。

下次接续教学前的内部检查：当前要实现什么；用户究竟卡在哪里；每个关键值由谁提供、流向哪里；解释中是否混入多个独立概念；代码落地和用户理解分别到了哪一步。检查结果用于调整回答，不让用户承担反复提醒的责任。
