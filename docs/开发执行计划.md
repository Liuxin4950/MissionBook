# Mission Book 开发执行计划

本文约束后续的学习式开发：依据最终产品规格反推结构，再按完整功能单元逐步教学，帮助用户理解 Flutter 的组件、布局、主题与业务实现。

## 1. 从最终结果反推

- 每个功能开始前，先阅读对应产品规格、设计规范和现有代码，明确最终布局、交互与数据职责。
- 先展示目标组件树和必要的目录变化，说明每个组件、文件负责什么，再开始写代码。
- 预先确定已知的结构要求，例如页面与导航壳的分工、安全区域、滚动方式、统一边距和主题归属。
- 后续步骤应在已确定的结构内增加内容，避免为了教学方便先写临时结构，随后再要求用户替换。
- 最终结构只覆盖当前规格，不为未来能力提前增加空接口、额外分层或未使用文件。

## 2. 按完整功能单元教学

- 一次完成一个能够理解、运行和观察结果的单元，例如“顶部布局与内容”或“日程标题与空状态”。
- 不把一个完整思路拆成“一次只增加一个 Text、Row 或属性”；也不一次交付整个页面及全部业务代码。
- 保持上下文连贯：说明这一步承接什么、完成什么、后续内容接在哪里。
- 用户反馈内容过多时，缩小功能范围，但保留该单元的完整结构和解释；不要退化成逐行挤出代码。

## 3. 解释选择与常见替代写法

- 给代码时，解释组件和关键属性的作用、为什么适合当前需求，以及省略后的默认行为。
- 对存在常见选择的地方，简要比较一到两种替代写法，再明确本次推荐及理由；不穷举所有 API，也不把一种写法说成唯一正确写法。
- 区分实现所必需的设置、设计效果所需的可选设置，以及框架或主题已经提供的默认设置，避免无理由重复配置。
- 遇到链式调用、工厂或辅助方法时，说明值从哪里来、返回什么类型、最终由哪个属性接收。
- 遇到主题时，区分 Flutter 默认值、项目统一配置和页面局部修改；说明修改是否影响全局，避免页面反复覆盖本应统一的样式。
- 解释放在相关代码附近，使用必要的注释和短段落，不把简单功能变成大篇幅 API 手册。

例如：顶部先说明 `Row → Expanded → Column + 按钮` 的空间关系，再解释 `Expanded` 与 `spaceBetween` 的取舍；使用 `styleFrom` 或 `copyWith` 时，解释它们生成的样式对象及适用场景。

## 4. 每轮教学流程

1. 检查当前代码，确认用户已经完成的部分，避免重复要求修改。
2. 给出本轮目标、最终组件结构和目录变化，只列实际涉及的少量文件。
3. 说明组件与写法的选择依据，然后给出代码，并明确新增、替换或保留的位置。
4. 提供可观察的验收结果，例如热重载后应看到什么、点击后应发生什么。
5. 简要交代下一单元与当前结构的衔接，不提前塞入下一单元的代码。

默认提供代码与指导，让用户亲自实现；用户明确要求代为修改时，再直接修改实现文件。用户提出概念问题时，先把当前问题讲清楚，不同时推进新的功能。

## 5. 避免不必要的返工

- 不用空回调、假业务数据或临时提示冒充已实现的功能；尚未接通的交互应明确标识。
- 能根据最终规格确定的容器和职责，在该功能第一次教学时就确定，不留到后面反复改写。
- 确实需要调整既有结构时，说明具体原因、影响范围和保留部分，区分新增需求、实际约束与前期设计遗漏。
- 不承诺永远不调整，但不能把可预见的结构遗漏当成正常教学步骤。

已发生的反例：今天页先使用最外层 `Column`，后续才根据早已存在的页面需求改为滚动容器，并删除导航壳中的重复顶栏。这些要求应在页面骨架设计时统一考虑，后续教学避免重复此过程。

## 6. 任务粒度与进度

- 按“页面骨架 → 完整界面区域 → 真实数据与业务交互”的依赖顺序推进；功能顺序仍须结合当前规格确定。
- 进度以现有代码和实际验收为准，明确区分静态布局完成、交互接通、数据持久化和运行验证。
- 示例代码、方案讨论或用户理解概念，不自动代表代码已经落地或功能已经验收。
- 开始下一单元前核对实际实现，不因教学节奏反复更换已确定的结构。
