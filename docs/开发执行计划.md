# Mission Book 开发执行计划

这份计划是开发路线和学习路线。最终范围以[本地应用规格](v1.0/本地应用规格.md)为准；每个阶段只实现当下可验收的一条切片，不先搭完所有实体、表和页面。

## 1. 目标与协作方式

先让用户能够真实创建一个独立 Mission，开始、结束、重启后仍能查看；再加入暂停、材料、截止、大纲、统计和通知。Windows 与 Android 都是最终交付平台，允许先在一个平台验证切片，然后在另一平台复核。

每次领取通常 20～90 分钟的小任务，按以下流程推进：

1. 说明任务解决的问题和位于哪一层。
2. 讲清马上用到的 Flutter / Dart 知识。
3. 核心代码优先由开发者亲手写；AI 给目标、必要接口、提示或小示例。
4. 共同检查代码和错误，解释数据流及设计原因。
5. 运行与改动相关的静态、自动和手工验证。
6. 能解释、能运行、能恢复后再作小步提交。

第一次接触时提供结构和解释，已练过时减少帮助；持续卡住再逐级补充示例，不一次生成作者无法维护的大架构。

## 2. 实现约束

- 六种 MissionPhase 从原始事实派生，页面、通知和统计使用同一查询。
- END 是用户报告唯一来源，ExecutionEvent 是执行过程唯一来源。
- 同一业务动作在一个事务内校验和写入，重复操作不重复追加事实。
- 开始后锁定方案和排期；取消只在开始前，放弃执行走未完成报告。
- 本次没有 AI、账号、同步、Plan 编辑器或其他未来占位功能。
- 某阶段暂未接入的当前功能明确标记为阶段限制，不冒充最终完成。
- 已经保存的学习数据也要迁移保留；新增表或列时递增 Schema，不通过删库绕过。

## 3. 架构与日常检查

按职责划分，不要求建立四套机械重复的类：

| 职责 | 内容 |
| --- | --- |
| Presentation | 页面、组件、表单和页面 Controller |
| Application | 创建、执行、材料等业务命令与事务协调 |
| Domain | 纯实体、事件合法性、阶段和时间计算 |
| Data | Drift、查询/仓库实现、文件、备份与通知适配 |

Domain 不依赖 Flutter 或数据库。页面调用用例，不直接同时修改多张表；Application 使用领域规则与必要存储接口，Data 实现接口，应用入口组装依赖。不要为每张表机械建立通用 Repository、事件总线或注入框架。

先用 ChangeNotifier、ListenableBuilder、构造器注入和 Navigator；遇到真实问题再判断是否引入第三方状态管理或路由。目录随切片增加，不第一天建空架子。

按改动范围运行：

```powershell
python tool/check_docs.py
dart format --output=none --set-exit-if-changed lib test
flutter analyze --no-pub
flutter test --no-pub
flutter run -d windows
flutter run -d <android-device-id>
```

没有 test 目录时先在阶段 0 建立最小测试基线。平台工具链和依赖没有准备好时先记录与修复环境问题，不把构建失败当成业务完成。

## 4. 分阶段路线

### 阶段 0：验证当前工程

学习入口、Widget 树、热重载、完整重启和测试命令。实际启动 Windows 和 Android 当前页面，建立最小 Widget Test，记录设备与检查结果。

验收：两端能运行当前模板，静态检查和最小测试通过。原计划曾记录 Flutter 3.41.2 / Dart 3.11.0 环境识别；这不是双端运行验收，当前版本仍以实际命令复核。

### 阶段 1：外壳与创建表单

建立暖白/墨绿主题、四个中文导航空页、任务标题/日期/计划时长表单和返回栈。先用局部内存保存理解数据流，明确此阶段重启不保留。

验收：创建临时任务能回到列表；输入错误和提交反馈可解释；窄屏、键盘和返回不丢未确认内容。

### 阶段 2：第一个持久化执行闭环

先支持独立任务、SELF_REPORT、FLEXIBLE。只实现这条路径需要的领域字段和五张表：missions、mission_schedule_revisions、execution_plans、execution_events、failure_records。

实现原子创建、Start、End（完成/未完成）、结果和最小历史查询。完成报告只来自 END；未完成同时有 FailureRecord，用户原因可空。首个 Schema 从 1 开始。

验收：创建 → 开始 → 完成/未完成 → 重启仍能看到原排期、END 与正确报告；事务失败无半条链。此阶段还没有暂停、材料或 Goal 归属，不提前建立未使用字段。

### 阶段 3：暂停、延长与恢复

补齐 Pause / Resume / Extend，事件 sequence、时间非递减、单个 RUNNING、派生 Phase 和纯时间计算。加入当前额度提醒，以及页面结束前先暂停的交互。恢复不依赖常驻计时器。

验收：运行/暂停时分别结束进程再打开，Focus 正确；暂停后 END、连续延长、重复按钮、旧通知预备动作和非法序列被正确处理；延长不改原计划。

### 阶段 4：可选材料与正式记录

加入 evidence 表，扩展可选材料策略、END 的用户选择和稍后放弃提交事实。实现草稿、复制附件、首次提交、结果预览和单条正式材料修正。

验收：整批提交原子保存且直接结束；可选材料可以晚些处理或放弃；草稿丢弃不删除正式附件，重启不承诺恢复草稿。SELF_REPORT 没有凭证入口，当前尚不开放强制材料。

### 阶段 5：强制材料、截止与开始前编辑

开放 REQUIRED_EVIDENCE、验收方向、排期截止字段、开始前编辑/改期/取消。校验当前完整策略矩阵；添加启动、前台与提交前截止补算。加入终态“再次尝试”并只保存 RETRY 血缘。

验收：截止前、恰好到期、重启补算、执行跨午夜、截止后 END、提交与超时竞争全部符合[领域规则](v1.0/领域模型.md#8-截止时间与失败记录)。取消无执行失败，执行后放弃必须 END；策略和排期开始后不可改。

### 阶段 6：Goal 与 GoalNode

新增 goals、goal_nodes 及任务可选归属字段，迁移保留已有独立任务。实现 Goal 编辑和状态、节点树、同级调序、子树归档/恢复、节点任务与记录覆盖率。

验收：关联、顺序和归档重启后保持；跨 Goal、循环和无效归属被拒绝。Goal 状态不改已有任务；节点完成只依据报告，不等待材料、不冒充掌握度。至此具备完整八张核心表。

### 阶段 7：大纲导入

按[输入协议](v1.0/数据落地与平台.md#5-goal-outline-导入)实现文件/粘贴、字节与递归上限、严格字段校验、预览和单事务创建。

验收：非法 JSON、未知字段、重复 key、错误类型、超限、取消确认、数据库失败都不留下部分目标；不把原始 JSON 当运行数据。

### 阶段 8：完整 Today、History、统计与备份

补齐跨日执行、全部日期待补材料和过去未开始任务入口。实现 7 天计划/完成、30 天完成格子、历史筛选、Me 与本地备份导出。

验收：跨日按 END 日期计一次完成，计划数与完成数分别显示；取消不混入执行完成，材料修正不重复计数；备份数据库快照和全部正式附件一致，失败不修改源数据。

### 阶段 9：本地通知

接入 FIXED 提醒、延后偏好、运行/暂停通知、陈旧 payload 防护与启动对账。业务提交与系统调度分开处理。

验收：延后不改排期或写执行事件，重启保留有效偏好；停止先暂停、取消确认保持暂停；拒绝权限不回滚业务事实。Windows 实际分发形态、Android 重启/强行停止/省电限制分别留真实证据。

### 阶段 10：双端完整验收与发布候选

在 Windows 和 Android 分别走完[本地应用规格](v1.0/本地应用规格.md#5-完成定义)的所有路径，包括杀进程恢复、附件、截止边界、权限失败、归档、导入和备份。

检查中文文案、图标、长文本、深层树、窄屏与键盘；执行迁移保留数据测试，构建 release 候选。手工验收结果、构建产物和剩余限制一起记录，不以构建成功代替产品验收。

## 5. 每阶段质量门槛

- 作者能说明数据从哪里来、操作经过哪里、为何这样保存。
- 格式化与静态检查通过；新增关键业务规则有必要的单元/数据库测试，关键交互有适当 Widget Test。
- 本阶段真实操作和恢复路径走通；没有用示例数据或模拟评价掩盖未实现。
- Schema 变化可迁移已有数据；通知或文件失败不破坏已保存事实。
- 文档随实际范围更新，通过文档检查；未验收内容不写已完成。
- 一个小任务对应可以准确描述的提交，不自动提交用户无关改动。

## 7. 第一个任务

从 0.1“认识并验证当前工程”开始：读懂 main → runApp → MaterialApp → Scaffold，在 Windows 修改标题验证 Hot Reload，再完成格式化、最小测试和 Android 运行。说明 Hot Reload、Hot Restart 与完整重启分别保留什么。

验收 0.1 后再领取后续任务；当前工作仅统一规格，没有代替开发者实现业务代码。
