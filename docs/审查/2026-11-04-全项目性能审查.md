# 2026-11-04 全项目性能审查

本次发现的高优先级问题集中在：AI 长回复的整段 Markdown 构建与重新进入后的重复解析、文字入口加载离线语音资源、隐藏页面重复全量读取历史，以及历史和目标目录随数据量放大的构建成本。已有的流式输出优化应保留，但它没有覆盖上述进入、回看和其他页面的路径。

性能问题的修复方向尚未落地。用户追加反馈的 AI 回复卡片过窄已经单独修正，详见 R01；原工作区已有的助手改动继续保留，不能把它们算作本轮修复，也不能据宽度修复声称 Android 卡顿已解决。

## 高优先级发现

### F01 · P1 · 长回复整段构建，回看和重新进入会再次付费

位置：[assistant_markdown.dart](../../lib/presentation/assistant/assistant_markdown.dart) 第 21、57 行；[assistant_page.dart](../../lib/presentation/assistant/assistant_page.dart) 第 439 行；[assistant_message_bubble.dart](../../lib/presentation/assistant/assistant_message_bubble.dart) 的 `_MessageBubble.build()`。

`AssistantMarkdown` 将一整条回复交给 `SelectionArea → MarkdownBody`。外层聊天列表虽然惰性构建消息，但单条长回复内部的段落、列表、代码块仍一次性建立。已有 `_cached` 只保存在该组件的 State 内；消息滚出列表缓存区域或页面退出后，State 销毁，回来需要重新解析和排版。

验证：一条含 160 小节、14,980 字符的样本挂载 18,132 个 Element；同样文字用单个 Text 对照只有 198 个。40 条消息的实际聊天页中，末条回复滚出后原 Markdown State 已销毁，滚回后是新 State。Android profile 的 8,080 字符回复在滚出后返回时出现约 143 ms（20 轮）和 1,068 ms（200 轮）的 UI 长帧。此步骤同时涉及变高列表重新定位/挂载，不能把整帧时间全部归给 Markdown 解析。主机 debug 只作工作量对照，不换算成手机帧率。

影响：首次打开最后一条长回复、回看长消息、退出后再进入，即使没有模型生成也可能卡顿。只隔离 token 通知或加 RepaintBoundary，无法减少首次解析和布局成本。

修复方向：按 Markdown 块建立惰性显示单元；为已完成消息采用有容量上限的解析结果缓存，键包含消息身份、内容版本和样式依赖；保持复制、选择、链接、过程与最终正文的原顺序。不要通过永久保活全部聊天历史换取缓存。

### F02 · P1（已安装离线模型时）· 文字聊天触发语音预热，释放链没有到达模型后端

位置：[assistant_page.dart](../../lib/presentation/assistant/assistant_page.dart) 第 119 行；[configured_assistant_speech.dart](../../lib/data/assistant/configured_assistant_speech.dart) 第 25、96 行；[assistant_speech.dart](../../lib/application/assistant/assistant_speech.dart) 第 218 行；[sherpa_worker.dart](../../lib/data/speech/sherpa_worker.dart) 第 13 行。

聊天页进入时就调用 `voice.warmUp()`。默认离线语音已安装时，接着执行 `_local.prepare()`，启动常驻 worker、建立 FFI 识别器，并做一次空音频预热。文字入口同样执行这一条链。模型清单中的 ONNX 文件为 239,233,841 字节，约 228 MiB，worker 配置两个线程；文件大小不能当作已测得的运行内存。

`AssistantVoiceController.dispose()` 最终只调用语音 `cancel()`；`ConfiguredAssistantSpeech.cancel()` 只撤销录音，未调用已有的 `LocalSpeechBackend.dispose()`。这使共享模型继续常驻，独立语音试用控制器反复创建/关闭还存在遗留 worker 的风险。

验证：文字聊天挂载时预热调用一次；注入“支持且模型已安装”的后端后，真实配置协作者执行 prepare，而关闭 VoiceController 没有调用后端 dispose。未在本轮主机加载 Android FFI 模型，也未实测其 PSS、CPU 或热降频。

修复方向：文字入口只装配语音能力；首次明确使用离线语音时再加载。由拥有者提供可等待的资源关闭路径，关闭试用控制器、切换语音方案及工作区重建时真正释放 worker。后台取消录音与销毁模型应有独立责任。

### F03 · P1 · 隐藏页面仍做全量历史查询，今天的待补查询也扫描全部结束任务

位置：[app_shell.dart](../../lib/app_shell.dart) 第 193 行；[mission_history_page.dart](../../lib/presentation/missions/history/mission_history_page.dart) 第 61 行；[me_page.dart](../../lib/presentation/me/me_page.dart) 第 96 行；[mission_evidence.dart](../../lib/data/repositories/mission_evidence.dart) 第 351 行。

四个主页面在 IndexedStack 中一并挂载。“历史”和“我的”即使不可见，也在初始化、业务 changes 和恢复前台时查完整结束任务；TickerMode 只处理动画/显式遵循它的计时器，不会取消这些查询。“今天”的 `findPendingEvidence()` 又调用 `findFinished()`，把全部结束任务装配成完整 MissionDetail 后再按阶段过滤。

验证：100 个自报结束任务、没有待补材料，只有今天页可见，仍执行三次完整结束任务读取，合计返回 1,800 行关联数据。一次 `refreshAfterExternalCommit()` 后再次发生同样的三次读取。三条路径分别来自今天待补、隐藏历史、隐藏我的。

影响：启动、回前台和助手执行任务写操作后，共享连接和 UI 数据转换会承担多个全量任务读取。快照序号能阻止旧结果覆盖页面，但不能停止已经发出的工作。

修复方向：首次访问再挂载主页面；非可见页面记录“需要刷新”，恢复可见时合并重读；我的页采用有界近期记录与专门统计查询；待补查询先用持久事实筛选候选，再使用完整阶段核心验证。不要新增另一套可写 phase，也不要为性能删除 STOP、reportPending 或截止维护。

### F04 · P1 · 历史分组为天数 × 记录数，图片读取也被提前启动

位置：[mission_history_page.dart](../../lib/presentation/missions/history/mission_history_page.dart) 第 212、227、433 行；[mission_queries.dart](../../lib/data/repositories/mission_queries.dart) 第 335 行。

页面先收集所有日期，再对每一天执行 `records.where(_day == day)`；每次比较还重新读取派生日期和解析 DateTime，复杂度为 O(D × N)。历史查询没有分页，所有 `_recordCard(record)` 都在构建 children 时执行。卡片存在图片时，`_thumbnail` 此时就启动文件读取，并把完整字节 Future 长期保留在 `_thumbnails`，不限于屏幕可见卡片。

验证：100 条、分属 100 天的历史读取返回 600 行；500 条、分属 500 天时返回 3,000 行。两组实际挂载的界面元素同为 933 个，说明屏幕外数据整理已成为显著成本。两轮主机 debug 采样，100 条构建约 0.82–1.23 秒，500 条约 7.95–17.34 秒。机器负载与调试环境影响较大，耗时不作为门槛，也不代表所有“500 条历史”都会等这么久，日期分散程度是明确触发条件。图片的内存峰值本轮未测。

修复方向：一次遍历生成按日分组索引，缓存每条记录的展示日期；先分页历史摘要，再按可见项构建卡片和读取缩略图；为文件字节缓存设置边界并在数据失效时清理。日期口径保持使用实际发生日期/现行补报规则。

### F05 · P1 · 目标目录一次挂载全部可展开节点，每行重复查找同级

位置：[goal_outline_section.dart](../../lib/presentation/goals/outline/goal_outline_section.dart) 第 131、441、504 行。

目录虽然计算了扁平 entries，但用 Column 为每个 entry 建立完整行；每行又从 all 中筛选 siblings 并定位顺序。默认展开的大目录会同时承受 O(V × N) 整理和所有行的布局成本。相同 service/goalId 的父级重建仍在 didUpdateWidget 的 else 分支重新查节点和任务。

验证：100 个顶层节点全部挂载，约 10,099 个 Element；500 个节点全部挂载，约 49,299 个 Element。两轮主机 debug 的构建分别约 0.79–1.66 秒和 2.57–4.23 秒。仅用相同参数重建父级也多发一次节点查询；测试未传 missionService，生产还会重读该目标任务。

修复方向：将可见 entries 交给惰性纵向列表；先按 parentId 建同级和位置索引；用真实数据修订/业务通知失效查询，而非每次父级更新无条件重读。继续保留节点身份、搜索、展开状态、排序和操作入口。

## 其他可定位的问题

### F06 · P2 · 冷入口先回放无关会话，日志计数也传回全部序号

位置：[assistant_configuration.dart](../../lib/application/assistant/assistant_configuration.dart) 第 97 行；[assistant_sessions.dart](../../lib/application/assistant/assistant_sessions.dart) 第 85 行；[drift_session_store.dart](../../lib/data/assistant/drift_session_store.dart) 第 203、279 行；[agent_runtime.dart](../../packages/agent_core/lib/src/sessions/agent_runtime.dart) 第 104 行。

initialize 固定打开最近会话，然后全局入口发现它属于对象，再关闭并打开全局会话。两个会话各有 200 轮时，实际先后打开 linked、global，回放 1,602 条日志、读取 14 页，第一份回放没有用于本次目标页。每个会话的 `_recordCount()` 还先把所有 sequence 查询回来取 length，之后再逐页读同一日志。

单会话 1,000 轮时，需要回放 4,001 条日志、32 页；包含计数的查询返回 8,005 行。两轮主机加载约 64–89 ms。当前“每次读 128 条”限制的是单次查询大小，打开页面前仍会读完整会话。Drift 生产原生连接默认使用后台数据库连接；JSON 解码、消息回放和页面投影仍在调用方，本结论不把 SQLite 本身误报成主线程执行。

修复方向：先按入口定位目标会话，避免无关回放；计数用 SQL 聚合。先显示页面/加载反馈和有界尾部记录，将完整恢复从路由首帧拆开；允许发送、继续或处理未知操作前，仍必须完成真实日志恢复、工具结算和租约校验。

### F07 · P2 · 聊天图片每次 build 解码 base64，破坏缩略图缓存身份

位置：[assistant_message_bubble.dart](../../lib/presentation/assistant/assistant_message_bubble.dart) 的 `_MessageImage.build()`。

`_MessageImage.build()` 每次 split 完整 data URL 并 base64Decode 为新的 Uint8List。即使 cacheWidth=480 限制了缩略图尺寸，新 MemoryImage 的字节身份仍变化。真实聊天页中让共享语音状态触发一次重建，前后 ImageProvider 缓存键不相等。多图消息会叠加主线程解码、分配和图像缓存开销。

修复方向：按消息/内容块身份缓存只读字节和 ImageProvider，内容变化时才失效，并限制总容量；保留原图查看能力。本轮没有测量多张 4 MiB 图片的内存峰值。

### F08 · P2 · 后台目标/节点总结逐子项串行查询

位置：[drift_analysis_store.dart](../../lib/data/analysis/drift_analysis_store.dart) 第 215、236 行；[drift_record_repository.dart](../../lib/data/repositories/drift_record_repository.dart) 第 411 行。

目标/节点 input 先列直接子项，再逐项 await child；每项读取总结任务状态、最近总结和对应类型的基础事实，共三个查询。普通浏览没有占用主模型时，自动队列可以走到此路径。大目标会长时间占用共享数据库队列，且产生大份上下文。

隔离真实仓储中，500 个直接节点的一次目标 input 执行 1,505 个 SELECT；采样见随附 JSON 的 `analysis_fanout`。修复应批量读取子项索引和最近版本，按现有直接归属口径装配；分块阶段检查中断。保留单串行分析、版本匹配发布和主会话抢占规则；10 秒空轮询用于读取事务触发的待办，不应直接删除。

### F09 · P2 · 用量提示仍在输入构建中做首次全量估算

位置：[assistant_composer.dart](../../lib/presentation/assistant/assistant_composer.dart) 第 447 行的 `_contextIndicator`；[assistant_controller.dart](../../lib/application/assistant/assistant_controller.dart) 第 364 行；[token_estimator.dart](../../packages/agent_core/lib/src/context/token_estimator.dart)。

输入区读取 estimatedContextTokens 时，仍扫描消息、建立完整前缀，首次或上下文变化时编码协议 JSON 并逐字符估算。工作区已有缓存后，1,000 轮样本的两轮缓存命中平均约 0.12–0.13 ms，首次约 21.55–33.70 ms。缓存命中已明显减轻成本，不能把它描述成每个 token 都重新估算全部正文。

修复方向：将估算结果随上下文修订发布为展示快照，避免在输入 getter 内首次做大计算；分清正文估算、未结算工具组和服务端实际用量。该项排序低于长回复渲染、资源加载和重复全量查询。

## R01 · 已修正：AI 回复卡片随内容收窄

用户在测试时追加反馈回复消息块过窄。`_MessageBubble` 的 Align 放松宽度约束，内部 ConstrainedBox 只给 maxWidth，因此较短的段落、列表或代码让整张卡片随内容收缩；流式气泡也只有 620 的宽度上限，完成后又换成 860 的上限。

本轮只对这一项修改产品代码：[assistant_message_bubble.dart](../../lib/presentation/assistant/assistant_message_bubble.dart) 的完成回答取得正文可用宽度，宽屏仍限制 860；生成中的回答采用相同宽度。用户消息继续自然收缩并右对齐，既有流式纯文本/稳定子树优化保留。

四组回归先失败后通过：320 宽双倍字号、390、768、1440 宽。修复前，390 宽页面的“收到。”卡片只有 75.5，正文可用 342；修复后为 342。Android 模拟器中，普通与双倍字号的实际卡片宽度均为 378.67，与扣除页面边距后的可用宽度一致；截图已实际查看。流式显示测试也验证生成中的卡片宽度，原复制回复与 48 触控目标继续通过。

这是显示宽度修复。F01–F09 的性能方向仍未实施，不能据两轮帧时间波动推断加速效果。

## 复验入口与修复顺序

采样代码均只使用隔离内存数据库、合成日志和注入设置/语音，不打开 `mission_book` 正式数据库，不加载真实 Key，不发模型请求。默认测试会跳过规模采样，只有显式开关才运行。

## 本轮验证记录

完整数据：[2026-11-04.json](性能采样/2026-11-04.json)。含 16 项主机采样、8 项 Windows 基线、8 项 Android 基线，以及宽度修复后的 8 项 Android 帧采样和 2 项布局测量。主机完整 16 项采样与 Android Gradle 编译时间重叠，debug 耗时受机器负载影响；元素数、查询数、状态销毁和资源调用等证据与耗时分开解读。

Android 两轮均使用 20/200 轮会话、末条 8,080 字符 Markdown、100 条结束任务。表内为 UI 阶段峰值，单位 ms：

| 场景 | 基线 20 轮 | 基线 200 轮 | 宽度修复后 20 轮 | 宽度修复后 200 轮 |

返回重新挂载时 raster 峰值约 1.94–2.81 ms，明显小于 UI 长帧；连续滚动两轮共采样约 1,466 帧，只有修复后 200 轮样本的一帧 raster 为 19.85 ms、超过 16.67 ms。进入时另有约 7.65–74.81 ms 的 raster 峰值，不能由这些数据排除字体/首次渲染等成本。一次冷启动的 660.95 ms 与后续运行不是稳定分布，不能作优化前后百分比比较。

`scroll_return_after_cull` 是跨越变高历史列表的强制跳转，包含列表定位、挂载、Markdown 构建和布局；普通手势滚动不能直接等同于该峰值。每组只有一次采样，入口总耗时还包括路由、输入焦点/键盘和 settle，不能当成单帧耗时或平均 FPS。截图转换在全部帧采样结束后执行，避免影响前面的渲染路径。

Windows profile 同样复现：进入 UI 峰值约 71–73 ms，退出重进约 69–83 ms，回看重建约 106/564 ms；已挂载区域的连续滚动没有超预算帧。Windows 基线没有包含随后新增的短回复布局集成用例。
