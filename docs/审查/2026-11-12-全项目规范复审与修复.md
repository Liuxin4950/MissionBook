# 2026-11-12 全项目规范复审与修复

> 按用户要求复审架构、UI、数据规范与逻辑漏洞。本轮最重要的结论不是缺陷清单，而是**审查方法**：以 v1.0 文档为验收基准、或从仓储 API 的输入空间推理，都会把有意设计判成缺陷。

## 方法纠正

首轮审查按 `docs/ui设计手册/` 与 `需求文档v1.0/` 判定"违规"，并从仓储可接受的输入构造失败用例。用户指出需求文档仍是 1.0、多处链路是后来为操作体验有意改的。复核后确认两类错误：

1. **拿过时文档当基准**：字号体系与备份入口层级都是 2026-10-31 / 11-03 的有意收敛，手册停在 10-23/25。
2. **从 API 输入空间而非真实用户路径推理**：构造了 UI 永远不会发出的调用，据此宣布核心功能失效。

此后所有结论均按"当前代码的真实调用链 + 用户可感知后果"复核，并区分确认缺陷、设计取舍与文档过时。

## 确认并修复

| 项 | 修复 |
| --- | --- |
| 附件修正只能换文件、不能只改说明（用户要求两者都能改） | 草稿默认沿用原材料；只改说明时 `insertEvidence` 以 sharedAttachment 跳过新建来源记录、record_id 留空，绕开 records 附件键唯一约束；换文件成为草稿内独立动作。**不改数据库结构**，schema 仍 16 |
| 备份排除 API Key 与本机资源（用户要求全资源导出） | 新增 BackupResource 勾选与导出前范围选择页；LocalResourceStore 按平台收集/写回安全存储、资料、动效、提醒偏好与已校验模型；恢复按包内真实内容判定类别 |
| ZIP 符号链接条目绕过解压炸弹防护 | 解码前先只读中央目录，拒绝目录与 UNIX 链接条目；archive 对链接会在 decodeBytes 内立即解压，事后检查来不及 |
| 附件只限字节、无像素上限 | 增加 4000 万像素上限（与助手图片同口径）；image 包自身尺寸异常也转成明确用户提示 |
| 提醒候选 LIMIT 64 落榜被当"已消失"并撤销 | 对账时按编号重读真实事实，只有确实已删除的才回收编号，其余继续同步 |
| referencedAttachmentKeys 每次全量解码归档 JSON | 归档键提取下推到 SQL 的 json_each / json_extract，沿用项目既有口径 |
| 孤儿附件要等用户打开编辑器才清理 | App 启动即调用一次协调器 initialize；已核实助手附件随消息内联持久化、不在附件目录，不会被误删 |
| JobService 重复启动覆盖 worker 泄漏引擎 | 加 null 守卫，完成回调始终用最新 JobParameters 结束作业 |
| 恢复中返回键静默无响应 | PopScope 补 onPopInvokedWithResult，说明正在校验或恢复 |
| 整份计划占用窗口忽略 EXTEND | 占用时长按"计划时长 + 已保存 EXTEND 累计"计算，与 fixedTimeSlotEnd 同口径 |
| reconcileEvidenceDeadlines 缺时钟守卫 | 与提交材料同口径，回拨时不写出早于结束事实的落库时刻 |
| END 错误文案仍写"只有执行中或暂停" | 改为包含已到点停止 |
| 助手权限档位命名 | 改为「询问 / 自动 / 完全」，完全档 AI 拥有最高操作权限；枚举标识与持久化值不变，旧配置不失效 |

## 有意保留，不作为缺陷

- **今天页周栏 FittedBox**：密集七列布局的取舍，仅 320dp + 2x 下"今天"两字缩到约 77%，仍可辨；改横滚会动到选中高亮与交互模型，风险大于收益。
- **照片 EXIF/GPS 原样保留**：用户明确"不考虑隐私"，且备份要求全资源；剥离会丢失拍摄信息。
- **单条坏数据整批查询 fail-loud**：有意设计，正常写入路径产生不了坏数据。
- **自定义模型端点允许 http**：用户自配；Android 平台默认禁明文，实际表现为连接失败而非泄露。
- **Web 端 flutter_secure_storage 密钥与密文同存 localStorage**：平台实现限制，非应用可控。
