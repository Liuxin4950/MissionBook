# 规范化数据、整包事务与稳定性

状态：2026-10-27 设计稿；当前数据库 schemaVersion=9，本轮没有迁移。字段见[协议](协议与字段.md)。

## 1. 保留核心模型，补齐真实入口

Goal 是方向，GoalNode 是树，Mission 是一次可执行行动；排期和执行方案仍分开。不要把整个导入 JSON 保存成一个大字符串，再让页面或调度器反复解析业务。

| 现有对象/表 | 导入时做什么 |
| --- | --- |
| Goal / goals | 新增 1 条 |
| GoalNode / goal_nodes | 按父先子后保存 N 条，数组顺序决定同级位置 |
| Mission / missions | 新增 M 条，所有任务关联新目标 |
| MissionScheduleRevision / mission_schedule_revisions | 每个任务新增首版排期 |
| ExecutionPlan / execution_plans | 每个任务新增唯一方案 |
| ExecutionEvent / execution_events | 新增 0 条 |
| Evidence / evidence_records | 新增 0 条 |
| FailureRecord / failure_records | 新增 0 条 |

当前创建入口不能直接接收 steps / notes，开始前编辑入口也缺少它们；这是应用契约缺口，不是 SQLite 字段缺失。实现时应让手工表单、导入和重试共用同一套创建及编辑规则，保留未编辑字段。没有必要为普通课程额外建 Plan、Course、AI 作者、评分或状态表。

### 必须共用的一致性规则

| 规则 | 承担位置 |
| --- | --- |
| 目标初始 ACTIVE，节点有效且同 Goal、无环 | 统一创建规则 + 整包仓储重验；现有组合外键兜底归属 |
| Mission 的 node 属于同一 Goal | 同一身份映射 + 当前归属触发器 |
| 每任务恰好一份方案、至少一条排期 | 整包事务保证完整链；方案 mission_id 唯一、排期 mission_id/revision 唯一 |
| 枚举、字段组合、时长、日期、时区、材料条件 | 从现有创建规则提取可复用校验，不只依赖表单；可表达的局部条件再由数据库 CHECK 兜底 |
| 开始前可改、开始后锁定 | 既有编辑与执行事务重读；导入不能绕开 |
| 历史追加、阶段派生、全局最多一个 RUNNING | 既有唯一执行核心和串行写入口；目标包不写执行事实 |
| 任意一条不合法不留下半包 | 外层事务 + 回执同提交 |

现有表的 CHECK 和外键并未包办所有跨行语义。新整包仓储不能绕过 MissionService 的输入规则直接把 Companion 写入当作业务通过；研究批写探针只证明存储和事务方向。

## 2. 文件键与数据库身份

~~~text
node key -> 新建 GoalNode UUID
mission key -> 新建 Mission UUID
mission.nodeKey -> 用前面的 node map 找 GoalNode UUID

每个 Mission UUID：
  -> 新建 ScheduleRevision UUID，missionId 指向它，版本 = 1
  -> 新建 ExecutionPlan UUID，missionId 指向它
~~~

先遍历节点生成映射，再解析全部任务引用；构建一次 Map 后每条引用为预期 O(1) 查询，总体 O(N+M)，不为每条任务扫描整棵树。

key 只用于输入校验、预览和本次构建，不按标题或数组位置充当永久身份。packageId 承担导入批次识别；后续“更新既有课次”若需要稳定外部任务映射，须另定义并迁移，不假装首版已支持。

UUID 与父子关系在首次准备提交时固定，失败保留同一请求；提交时间在写事务内统一捕获。事务失败且进程丢失后允许重新准备，因为失败事务不存在半批持久化数据。

## 3. 为什么建议增加导入回执

当前目标导入只在内存保留同一次请求，重新选择文件会分配新 UUID。即使所有业务对象已经支持按 id 重试，也无法识别“这份课标昨天已经导入过”。

建议在真正实施新协议时增加一张有实际用途的技术表 import_receipts：

| 字段 | 作用 |
| --- | --- |
| schema_name / package_id | 组成唯一键，识别同一协议家族的外部包；升级版本不重置包身份 |
| schema_version | 首次成功导入的协议版本 |
| payload_sha256 | 严格解析后的最终确认 JSON 的规范化内容摘要 |
| content_sha256 | 排除 packageId 后的规范化内容摘要，非唯一索引用于提示“相同计划换了包编号” |
| goal_id | 指向本次创建的新目标，不能级联物理删除 |
| imported_at | 实际成功提交的 UTC 毫秒时刻 |
| node_count / mission_count | 显示导入结果的原始数量，不作为当前业务统计 |

这是导入幂等凭据，不保存原始 JSON，不引入 AI 评价或空占位表。它只在整包成功时出现，与创建的业务数据同一事务提交。

当前“八张核心业务表”可保留；将来技术回执使实际表数增加，不该为了守住旧表数量牺牲真实可靠性。数据库升级版本在实施时根据当时最新 schema 确定，不在本轮硬写为已经升级到 v10。

## 4. 包身份与内容摘要

建议 SHA-256 的输入采用 RFC 8785 JCS 规范化的最终 JSON：对象属性顺序和空白变化不改变摘要，数组顺序保留、字符串内容变化会改变摘要。遵循 [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785) 的规范化要求；不能用原始文本 hash 或随便一次 jsonEncode 冒充 JCS。

- 先拒绝重复对象键、非法 Unicode 和超限输入，再规范化。
- 本协议数字只承载受限整数，不引入浮点时长、NaN 或无限数。
- 摘要前不擅自归并语义相近的字符串、时刻或省略字段。显式默认值与省略默认值可被视为不同载荷；同 packageId 改写它们应提示内容冲突。content_sha256 仅排除 packageId，服务于重复内容提示，不冒充语义等价识别。
- 批量改期等草稿转换要先反映到最终确认 JSON，再算摘要。本地“允许冲突”等确认选项不改变内容，不加入内容摘要。
- 确认前将默认值、UTC 时刻等展开为不可变预览结果。提交时重新计算并比较；若规则、时区数据或内容变化造成实际写入结果不同，要求重新预览。

| 回执状态 | 处理 |
| --- | --- |
| 同包身份，不存在回执 | 进入完整校验与创建 |
| 同包身份，摘要相同 | 返回原 goal_id 和原导入数量，不新增，不重置目标或任务 |
| 同包身份，摘要不同 | PACKAGE_ID_CONFLICT，不更新、不覆盖 |
| 内容相同，换了 packageId | 视为明确的新包；预览提示可能是副本，确认才新建 |

回执查重必须早于“截止是否已过、目标是否 ACTIVE”等时变业务校验。同包首次成功后，目标可能已经暂停、任务已经执行、材料截止已经过去，再次选择应返回原成功结果，而不是重验旧创建条件后报错。

不得靠当前可编辑标题、排期或目标状态判断是否为同一次历史导入。回执解决的是首次提交身份，不表示当前目标内容仍等于导入时内容。

## 5. 一次提交的顺序

### 事务以前

1. 按 1 万任务目标限制字节、深度和值数量，使用流式 UTF-8 / JSON 解码，不先生成整棵 AST。
2. 在独立暂存库中保存已校验输入、索引化 key、解析后排期和固定身份；跨引用及内容摘要校验完成后封存暂存作业。
3. 方案正文放暂存存储，内存仅保留有界批次和必要索引；预览分页读取，按当前业务库生成冲突及过期提示。
4. 用户在既有导入区确认最终内容，固定暂存摘要与预览结果，正式业务仍然零写入。

系统文件选择、图片读取、网络 AI、用户输入和图片复制都不能跨在数据库事务里面。本协议不导入附件，自然也不需要预复制材料。

### 事务里面

1. 沿用与任务执行/目标编辑兼容的 SQLite 串行写边界，取得写权限后再读。
2. 查询回执；同包同摘要直接返回，不生成新的业务记录。
3. 对新包捕获一次创建业务时刻，重验绝对截止、当前时段选项、已有任务冲突及封存预览内容。
4. 保存 Goal；父节点先于子节点保存全部 GoalNode。
5. 从已封存暂存库按有界批次读取，保存全部 Mission、对应的唯一 ExecutionPlan 和首条排期。batch 同时受条数和字节预算约束，外层仍是同一个事务。
6. 保存唯一 ImportReceipt；任意写入或关联检查失败都回滚整个包。
7. 写入结束、COMMIT 前再次做时间门槛检查，防止长批次跨过强制截止或未经允许的立即开始边界；记录创建时刻不重新分配。等待全部操作后提交，不使用吞错误的冲突忽略模式。

Drift 事务要求等待内部数据库操作完成；事务中途创建异步任务却不等待会破坏边界，参见 [Drift 官方事务说明](https://drift.simonbinder.eu/dart_api/transactions/)。

### 事务以后

返回包含 goalId、原始数量、是否重复提交的导入结果。目标与任务服务各发送一次变化通知，让既有页面及调度器重读；不能在循环每保存一个任务就通知一次。

通知失败和调度失败有独立的重试反馈，业务数据已经成功时不把导入按钮恢复成“再创建一次”。进程在提交后、通知前退出时，下次启动按数据库和回执恢复并对账。

## 6. 并发与失败矩阵

| 场景 | 必须保证 |
| --- | --- |
| 双击确认、主引擎和后台连接同时处理 | 唯一回执和数据库写边界保证只创建一次 |
| 第 K 个节点或第 K 个任务保存失败 | 目标、节点、三件套和回执全部不存在 |
| 提交成功、响应丢失 | 重试返回原结果 |
| 提交前被杀进程 | SQLite 回滚未提交批次，重新导入可成功 |
| 提交后被杀进程 | 原目标与全部任务存在，回执可确认成功 |
| 预览后有人改期或开始任务 | 事务内重新检查，必要时原位刷新预览再确认 |
| 预览期间强制材料截止已过 | 不留下半包，明确定位截止错误 |
| 系统时间倒退或变化 | 重新核对时间条件，不倒填执行事件；不复用过期预览 |
| 之后用户修改了目标或任务 | 原回执仍返回原身份，不覆盖后续修改 |

不能把“只用了 transaction”或 UI 禁用了按钮当作这些场景已经验证。需要两条独立数据库连接及文件重开测试。

## 7. 效率与现有瓶颈

[本日功能审查](../../开发/审查记录/2026-10-27-lib功能审查.md)已有宿主探针证据：独立任务全详情查询 10 项为 41 次 SELECT，100 项为 401 次 SELECT；实际材料查询为全表扫描。调度器和通知还会读全量详情。有归属时目标/节点查询也可能重复。

因此新协议不能只做批量 INSERT：

- 自动开始先按最新排期、无 START、未取消筛选候选，不在写锁内加载全部历史材料。
- 列表、历史及目标摘要按需要批量查询，使用既有唯一阶段规则装配完整事实，避免逐任务多次 SELECT。
- 首先针对真实 WHERE / ORDER BY 检查索引，尤其 evidence_records(mission_id, submitted_at, id)；字段顺序和是否能消除排序以 EXPLAIN QUERY PLAN 为准。
- 根据实际候选查询评估排期的日期/开始时刻索引、最新版本取得方式及 START 反查；不凭感觉堆索引。
- 到点候选还要过滤已错过整个时段的旧计划；不能仅用 fixedStartAt <= now 把多年旧待办全部装配。评估开始与计划结束表达式的查询条件/索引，以实际查询计划和多年历史数据验证，不假定所有手工任务都不超过 24 小时。
- 预览列表按可见项构建，树默认折叠，错误明细分页；不一次构造 10000 张完整编辑表单。
- 文件用有界流读取到暂存存储，不让原始字符串、完整 AST 和全部领域对象在内存各存一份；文件大小不等于内存峰值。

索引必须有旧库保数据迁移和查询计划验证；不为省查询新增可写 phase、可写进度或跨事务复用旧事实。

## 9. 数据更新边界

首版没有 Merge / Replace；原因是它们需要回答“同名是否同一个节点、已开始任务怎么办、删除是否归档、什么算用户后改内容”。这些不能靠字符串相等安全推断。

后续真实需要追加课次时，单独设计“目标引用 + 新任务集”的命令，事务内校验目标 ACTIVE 和节点有效。需要更新时，再增加稳定外部映射、旧版本前置条件、差异预览及只修改未开始任务的规则；原执行历史保留。这些不是首版 JSON 中已经能用的字段。
