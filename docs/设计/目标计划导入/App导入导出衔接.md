# Goal 契约确定后的 App 导入导出

2026-10-27：按用户要求，先确定 Goal 数据结构、规则和容错，再完善 App 的导入导出。本文先固定边界与必答问题，不提前宣称完整恢复格式已经定稿或实现。

## 1. 三种不同用途

| 用途 | 内容 | 导入时意味着什么 |
| --- | --- | --- |
| 计划模板交换 | 目标、节点、任务、排期、方案 | 创建一份新的可执行计划，不恢复执行历史 |
| 单 Goal 完整归档 | 一个 Goal 关联的全部真实记录及材料 | 精确保留身份和历史，需要专门定义归档恢复/冲突 |
| App 完整备份与恢复 | 整库、全部正式附件、必要配置及版本 | 在一致快照上完整恢复，不等于合并一个计划包 |

不能把其中一个 JSON/ZIP 的成功导出说成三个能力都具备。恢复规则与模板创建规则也不能共用“所有状态都重置成 ACTIVE”。

## 2. 现有代码边界

[DatabaseBackupService](../../../lib/data/backup/database_backup_service.dart)当前导出一致事务中的 database.sql、正式附件、manifest.json 和说明文件；未提交草稿不导出，应用没有恢复入口。

当前接口 BackupExporter.create 返回完整 Uint8List，代码会把 SQL、附件字节和最终 ZIP 同时放在内存中，并在读事务里等待附件。已有[功能审查 R08](../../开发/审查记录/2026-10-27-lib功能审查.md)证实它会让其他数据库操作等待；不能把当前实现直接扩成无限量全量备份。

后续增加导入回执、设置范围或新表时，manifest、导出说明、快照、迁移和恢复测试都要一起更新，不能继续写死“八表”而遗漏技术记录。

## 3. Goal 计划导出如何对称

待 goal-package 稳定后，再增加目标详情中的“导出计划模板”：

- 输出同一套严格协议，导出后应能通过相同校验。
- 导出的 key 由应用为文件内引用生成，不把数据库主键塞进 id 字段。
- 为新模板生成新的 packageId，并明确这是新的创建包；不能复用原回执身份导致换设备/本机重导语义混乱。
- 必须明确导出哪些任务：建议默认选未开始任务；若用户选择历史任务的方案，则明确只复制计划并重新安排日期，不复制完成事实。
- 若选择某个节点，导出引用所需的完整祖先链；不能产生悬空 nodeKey。
- 归档节点、已取消任务、过期排期及强制材料截止应给出明确选择和计数；不能静默漏掉。
- 超过同一协议限制时停止并说明，不能输出一个应用自己无法导入的文件，也不能悄悄截到前 10000 条。

这类模板不是原数据的无损备份；若要保留真实材料、事件和状态，使用完整归档格式。

## 4. App 完整归档必须先定的问题

| 问题 | 待定契约 |
| --- | --- |
| 身份 | 原 ID 是否保留、相同 ID 不同内容如何判定，导入回执如何保留 |
| 范围 | 领域表、技术回执、个人资料、提醒偏好各自是否包含 |
| 版本 | 归档协议版本、数据库版本、最低应用兼容版本分别记录 |
| 附件 | 清单、大小、SHA-256、相对路径、类型和正式引用闭包 |
| 时间 | UTC 原值、时区、排期版本、事件序号及真实提交时间不重造 |
| 恢复模式 | 首版建议完整替换恢复，合并另行设计 |
| 活动任务 | 恢复包含 RUNNING 时如何防止与当前库运行事实冲突 |
| 回退 | 完整恢复失败前后的原库和正式附件怎样保全 |
| 导出验证 | 归档能否在隔离库恢复并逐字段核对，不只看 ZIP 能打开 |

完整替换恢复前先为当前数据保留可用快照，校验新库和附件全部通过后，再在连接受控关闭时切换。不能边解析外部文件边覆盖当前业务库。

SQL 备份中的语句不应直接在正在使用的主库执行。恢复格式定稿时需选择受约束的结构化导入或受控隔离恢复，验证表、索引、触发器、版本和完整性；不能让任意附带 SQL 指令成为运行入口。

## 5. 大归档的资源与损坏处理

- manifest 先校验：条目数、声明大小、总解压字节及支持版本。
- 分块读写及压缩，输出到临时目标，最终成功再交付；不能全部附件常驻内存。
- 对每个附件校验实际大小和摘要，不依赖压缩包声明值。
- 拒绝绝对路径、父目录穿越、重复条目和超预算解压；解压到隔离目录。
- 截断、缺失附件、磁盘不足、取消或校验失败时，原库保持可用，临时文件可清理。
- 导出快照和正式附件清单一致后尽快释放数据库连接；附件归档在事务外继续完成，不能让相机/文件 IO 长期占住事务。
- 准确表达“已生成临时归档”“已交给系统保存”“用户实际保存成功”的不同证据。

## 6. 顺序与本轮边界

1. 先确定 Goal、Node、Mission 的导入字段、默认值、去重、事务和资源预算。
2. 实施并验证小规模真实课标闭环，再验证目标数据量。
3. 用同一 Goal 契约实现对称的计划模板导出。
4. 另行定稿单 Goal 完整归档和 App 完整备份恢复，再处理合并、跨设备及旧版本兼容。

当前用户补充的是设计顺序与质量要求；本轮没有实施导出重构或恢复，也不把这些后续章节当作已获确认的全部产品选择。
