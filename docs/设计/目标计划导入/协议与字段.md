# 目标包协议与完整字段

状态：2026-10-27 设计稿；入口见[总览](总览.md)。机器结构以同目录 [JSON Schema](mission-book.goal-package.v1.schema.json) 为准，本文补充存储映射和必须执行的业务检查。

## 1. 协议身份与兼容

| 字段 | 必须 | 取值或规则 |
| --- | --- | --- |
| schema | 是 | 固定为 mission-book.goal-package |
| version | 是 | 整数 1，不接受字符串或其他版本 |
| packageId | 是 | 用户或外部生成工具固定的导入包身份，1–128 个小写字母、数字、点、下划线、短横线，首字符为字母或数字 |
| goal | 是 | 新目标的内容 |
| defaults | 是 | 本包默认排期时区、分钟数、材料策略 |
| nodes | 是 | 完整节点树数组，可空 |
| missions | 是 | 具体任务数组，可空 |

packageId 不是数据库 Goal.id，也不应在每次重试时重新生成。同一包重复选择沿用它；确实要新建一份独立副本才换编号。重试、修改已导入计划和复制课程是三个不同操作。

旧 mission-book.goal-outline v1 仍只接收 schema / version / goal / nodes，不向旧协议偷偷添加 missions。JSON 协议版本、数据库 schemaVersion 和文档目录中的“v1.0”分别演进，不能混用。

## 2. 目标与节点

| 对象 | 字段 | 必须 | 处理及去向 |
| --- | --- | --- | --- |
| goal | title | 是 | 非空标题 → Goal.title |
| goal | description / why | 否 | 用户给出的目标说明和动机 → 同名字段 |
| node | key | 是 | 本文件节点唯一键，仅用于引用及映射，不是数据库主键 |
| node | title | 是 | → GoalNode.title |
| node | description | 否 | → GoalNode.description |
| node | children | 否 | 省略等同 []；嵌套位置决定父节点 |

同级数组顺序决定 orderIndex，从 0 连续编号；没有可让外部指定的 parentNodeId、orderIndex、goalId、status 或 archivedAt。

所有节点 key 在整棵树内唯一。节点和任务的 key 分属两个命名空间，各自去重；nodeKey 只查节点集合。不按标题匹配，两个同名章节也不会误关联。

根节点为第 1 层，整棵树最多 12 层、500 个节点；Schema 的单个数组 maxItems 不能替代全树总数检查。

## 3. 每个任务

| 字段 | 必须 | 处理及去向 |
| --- | --- | --- |
| key | 是 | 本包任务唯一键，1–64 个受限 ASCII 字符 |
| nodeKey | 否 | 解析为新树中的 GoalNode.id；省略表示只关联新 Goal |
| title | 是 | → Mission.title |
| description / why | 否 | → Mission.description / why，不擅自复制目标动机 |
| verificationPolicy | 否 | 覆盖 defaults.verificationPolicy → Mission.verificationPolicy |
| schedule | 是 | 完整排期输入，展开后成为首条 MissionScheduleRevision |
| executionPlan | 否 | 方案输入，展开后恰好生成一个 ExecutionPlan |

本协议是“一个新目标及它的任务”，所以每个任务都会取得这个 Goal.id；不支持在同一包混入独立任务或引用其他目标。应用原有独立任务创建能力保留。

同一个节点可以被多个任务引用；非叶节点也允许直接关联任务。一个任务只直接关联一个节点，不把一节综合课擅自记成多个节点完成。

## 4. 排期输入

| schedule 字段 | 必须 | 处理及去向 |
| --- | --- | --- |
| scheduledDate | 是 | 排期时区内的真实日历日期，严格 YYYY-MM-DD |
| timePolicy | 是 | FIXED 或 FLEXIBLE，每个任务显式选择 |
| timeZone | 否 | 覆盖包默认值；解析为可识别的 IANA 时区 |
| plannedDurationMinutes | 否 | 覆盖默认值；本协议建议限定 1–1440 的整数分钟 |
| fixedStartAt | FIXED 必须 | 带 Z 或明确偏移的绝对时刻 → UTC 保存 |
| evidenceDeadlineAt | 条件 | 仅有效策略为 REQUIRED_EVIDENCE 时允许；省略则计算次日零点 |

FLEXIBLE 必须不出现 fixedStartAt，不能用 null 代替省略。

plannedDurationMinutes 的 1440 上限是本次导入输入的保护建议，当前普通创建只要求大于 0。不能把该上限误称为既有领域限制；今后确有长任务需求可连同协议约束调整。

所有绝对时刻采用本协议的 RFC 3339 子集：大写 T / Z、必须有秒、最多 3 位小数秒、明确时区偏移；不接受无偏移时间、闰秒、24:00 或 -00:00。日期和时间还必须做真实日历校验。

## 5. 执行方案

| executionPlan 字段 | 必须 | 展开结果 |
| --- | --- | --- |
| objective | 否 | 省略时采用任务 title；这是要完成的具体结果 |
| steps | 否 | 有序的非空字符串数组，省略为 [] |
| verificationCriteria | 条件 | 强制材料必须非空；其他策略选填 |
| notes | 否 | 方案补充说明，省略为 null |

方案整个对象省略时，也生成 objective=title、steps=[]、其他为空的真实 ExecutionPlan。若有效策略为强制材料，则不允许省略必要的 verificationCriteria。

JSON Schema 无法直接表达“任务策略省略时继承根 defaults，再决定嵌套字段必填”。因此必须先展开有效策略，再运行统一材料规则；不能把 Schema 通过当成业务通过。

steps 只作为展示和执行说明保存，不自动运行代码、不解释为系统命令，也不意味着系统逐步确认或采集了动作。当前没有单步打卡实体，不能把 steps 数量当成完成次数。

## 6. 默认值如何展开

| 最终值 | 来源顺序 |
| --- | --- |
| timeZone | schedule.timeZone → defaults.timeZone |
| plannedDurationMinutes | schedule.plannedDurationMinutes → defaults.plannedDurationMinutes |
| verificationPolicy | mission.verificationPolicy → defaults.verificationPolicy |
| objective | executionPlan.objective → mission.title |
| steps | executionPlan.steps → [] |
| evidenceDeadlineAt | 显式值 → 仅强制材料时计算排期日次日零点 |

只有这张表列出的项可以补默认值。没有默认日期、默认“晚上”、默认固定开始时刻，也不以当前设备时区代替文件时区。Why 和验收要求等真实内容不足时，不能编造补齐。

defaults 三个字段全部显式提供，避免使用者不知道本包最终继承了什么。Schema 中没有靠 default 关键字代替转换代码。

## 7. 应用负责生成的字段

| 对象 | 由应用生成的内容 |
| --- | --- |
| Goal | UUID、ACTIVE、createdAt / updatedAt |
| GoalNode | UUID、新 Goal.id、parentNodeId、orderIndex、空 archivedAt、创建时间 |
| Mission | UUID、新 Goal.id、映射后的可空 goalNodeId、空取消/放弃/重试来源、创建时间 |
| ScheduleRevision | UUID、missionId、revisionNumber=1、changedAt，UTC 开始与截止 |
| ExecutionPlan | UUID、missionId、createdAt / updatedAt |
| ImportReceipt | 包身份、载荷及去包编号内容摘要、新 Goal.id、提交时刻及数量 |

本次创建请求的身份在首次准备时固定，数据库事务内捕获一次实际提交业务时刻作为新记录创建时间，并在同一次写入中保持一致；已成功请求由回执返回原结果，不重建时间。

## 8. 不允许导入的字段

所有对象都拒绝未知字段，并给出具体 JSON Pointer。下列内容尤其不能混进计划输入：

- 数据库 id / missionId / goalId / goalNodeId、parentNodeId、revisionNumber。
- phase、status、progress、mastery、score、实际开始/结束、createdAt / updatedAt。
- executionEvents、evidence、failureRecords、完成报告、cancelledAt、evidenceWaivedAt。
- sourceMissionId / relationType；新课程课次不是旧任务重试。
- 自动结束、强制抢占、单任务提醒偏好、未经支持的 recurrence / dependsOn。

不知道的内容要在生成前补充约束，或省略允许省略的字段，不能塞入随意的新键后指望应用忽略。

## 9. 类型、文本及文件边界

- 用户规模目标为单 Goal 10000 个任务。UTF-8 文件建议上限 32 MiB，必须有界流读及磁盘暂存；粘贴入口仍限 2 MiB，大计划走文件。两种入口共享字段和业务规则，但不承诺相同容量。旧 goal-outline 仍维持当前 2 MiB 限制。
- 不接受 JSON 外围说明、Markdown 围栏、注释或尾逗号。首版建议严格拒绝 BOM，界面提示重新保存为 UTF-8 无 BOM。
- 全局 JSON 嵌套深度建议最多 64，先用有预算的解析器防止异常输入，再检查节点树 12 层限制。
- 最多 10000 个任务；全包最多 100000 个步骤、1000000 个 JSON 值。具体保护与验收见[容错与大数据量](容错与大数据量.md)，初次真实可行性试验仍先使用 5–20 个任务。
- 标题及 objective 最多 200 个 Unicode 码点；说明、动机、备注、验收方向最多 20000；每个步骤最多 2000、最多 100 步。校验器须统一码点长度，不能直接拿 Dart UTF-16 length 当作等价口径。
- 必填文本 trim 后非空；选填普通文本为空时转 null。key 不 trim、严格按 Schema 匹配，防止引用悄悄改变。
- 所有可选键省略表示未填写，显式 null 拒绝。数组省略的默认含义仅限文中明确列出的字段。
- 原始 JSON 对象若出现同名键必须拒绝；普通 jsonDecode 后键已折叠，仅检查 Map 无法发现。
- 数字字段还需按本协议检查解码后为真正整数类型，拒绝 bool、浮点写法和指数写法。JSON Schema 的 integer 按数值判定，可能接受 1.0，不能单靠它证明 Dart 输入契约成立。

## 10. 错误返回

错误包含 code / path / message，可额外给出 relatedPath；例如：

~~~json
{
  "code": "UNKNOWN_NODE_KEY",
  "path": "/missions/2/nodeKey",
  "message": "未找到节点 adaptive-layuot",
  "relatedPath": "/nodes"
}
~~~

建议分类：INVALID_JSON、DUPLICATE_FIELD、UNKNOWN_FIELD、UNSUPPORTED_SCHEMA、LIMIT_EXCEEDED、DUPLICATE_NODE_KEY、DUPLICATE_MISSION_KEY、UNKNOWN_NODE_KEY、INVALID_DATE、UNKNOWN_TIME_ZONE、OFFSET_ZONE_MISMATCH、INVALID_DEADLINE、SCHEDULE_CONFLICT、PREVIEW_STALE、PACKAGE_ID_CONFLICT。

结构错误、关联错误、业务错误都在写入前完整定位；提交时仍可能出现并发变化或到期，需要重验并保留输入。错误不能被当成“忽略这条任务继续导入”。
