# 容错、资源边界与超大 Goal

2026-10-27，按用户“大数据量不能把应用导入炸掉”和“单 Goal 约 1 万个任务”的补充约束形成。本文是待实施契约，不声称当前代码已经具备全部保护；入口见[总览](总览.md)。

## 1. 安全拒绝和支持大规模是两件事

本轮按单 Goal 10000 个任务设计，同时保证超限输入被明确拒绝，已有数据完整、界面能恢复。不能把“限制文件大小”称为已经支持任意大 Goal，也不能只增加上限就宣称性能改善。

需要同时控制：

~~~text
来源文件 → 原始字节 → JSON 结构 → 全量业务校验
        → 预览 → 数据库写入 → 提交后查询/调度 → 长期累计数据
~~~

同一份文件可能同时存在为字节、Dart 字符串、解析树、领域对象、列表组件和数据库写参数。输入 32 MiB 绝不意味着内存只占 32 MiB；后台解析也不减少总内存，它主要隔离耗时。

## 2. 首版资源预算建议

| 资源 | 建议硬边界 | 检查位置 |
| --- | --- | --- |
| 文件 UTF-8 | 32 MiB 原始输入 | 读取前元数据、流读取中和解析前 |
| 粘贴 UTF-8 | 2 MiB；更大内容走文件 | 输入接收与变更入口、解析前 |
| JSON 容器嵌套 | 64 层 | 有预算的 tokenizer / parser，不能解码后才看 |
| JSON 值总数 | 1000000，包含对象、数组及标量 | 解析中计数，不把巨大空数组先完整建立 |
| 节点总数 / 树深 | 500 / 12 | 解析与语义遍历 |
| 任务总数 | 10000 | 解析任务数组时及时停止 |
| 步骤总数 | 全包 100000，每任务 100 | 解析/语义阶段双重计数 |
| 单任务紧凑 JSON | 256 KiB | 限制正在解析的单个大对象 |
| 文件读取块 | 建议 64 KiB | 原生流 / Web Blob.slice 分块 |
| 暂存/提交内存批次 | 建议最多 100 条，且最多 1 MiB，先到先切块 | 暂存与正式提交 |
| 预览页 | 建议 50 条 | 从暂存索引分页，不加载 1 万条正文 |
| 字段长度 | 按字段协议，统一 Unicode 码点 | 字符串读取中及结构校验 |
| 一次报告错误 | 最多 100 条，加“还有错误”说明 | 校验阶段 |
| 展示冲突对 | 最多 200 对，保留准确受影响任务摘要 | 冲突检测和预览 |
| 完整表单/预览项 | 仅构建可见项，分页或虚拟滚动 | UI |

这些是待设备验证的保护建议，不是性能承诺；最大字节、数量和长度同时生效，任一先达到即拒绝，用户文件不能自行提高预算。Schema 表达局部限制，值总数、全包步骤和全树节点等必须由解析器/业务代码补足。

最大记录数量也是有界的：1 Goal + 500 Node + 10000×3 任务三件套 + 1 回执 = 30502 条新增记录；这只界定写入工作量，不代表 30502 条写入已经在目标设备测得足够快。

首次真实使用仍从 5–20 个任务开始，独立压力库必须覆盖 1 万，不在用户数据库压测。超过 1 万、500 节点或 32 MiB 时明确拒绝；不能据此承诺 10 万任务也支持。节点规模暂按现有 500 保护预算，用户给出的 1 万是任务量，二者不等同。

## 3. 保留当前已有的读取保护

已核对当前实现：

- [原生文件入口](../../../lib/data/goal_import/goal_file_picker_native.dart)先读取 file.length，再从 openRead 逐块读取并检查累计大小；不是先把任意大文件完整装进内存。
- [Web 文件入口](../../../lib/data/goal_import/goal_file_picker_web.dart)先检查 File.size，读取 arrayBuffer 后再次核对字节数。
- [当前解析器](../../../lib/application/goals/goal_outline_parser.dart)在 UTF-8 / JSON 解析前检查 2 MiB，并检查大纲总数和树深。

新协议保留这些保护思路，但需把“返回完整 pickBytes”的来源接口改为可流读来源，再补原始 JSON 深度/值预算、重复对象键和粘贴入口限制。旧仅大纲入口仍用当前 2 MiB 规则，不一起放大。

文件元数据可能不准确，累计实际字节检查仍必须保留。粘贴文本已有系统剪贴板和输入框分配成本，应在接收/变更入口限制字符预算，并在正式转换时检查 UTF-8 字节，不等建立多份预览后才拒绝。

## 4. 各阶段的容错责任

| 阶段 | 失败例子 | 处理 |
| --- | --- | --- |
| 文件读取 | 取消选择、权限失效、读取中断、大小变化 | 释放流和缓冲，保留原草稿，业务零写入 |
| 解码 | 非 UTF-8、BOM、截断、多份 JSON 拼接 | 拒绝并定位，不猜着修补 |
| 原始结构 | 极深嵌套、超量值、超长文本、重复字段 | 预算触发即停止，不能依赖捕获 OOM 自救 |
| 结构字段 | 类型错、未知键、版本不支持 | 有界错误列表，零写入 |
| 业务关系 | 重复 key、悬空 nodeKey、截止不合法 | 整包拒绝，不跳过坏任务 |
| 预览 | 用户取消、文件内容改变、其他入口改期 | 取消零写入；变化后重新校验确认 |
| 提交 | 磁盘不足、锁忙、外键失败、约束冲突 | 事务回滚，保留固定请求；锁忙有限重试 |
| 结果不明 | 提交后响应丢失、页面关闭 | 查持久化回执确认，不能按“未知”重新分配包 |
| 提交后 | 调度/通知失败、页面查询失败 | 数据已成功；单独重试刷新/提醒，不再创建 |
| 重启 | 临时工作未完成或提交已完成 | 清理无业务引用临时文件；回执确认最终事实 |

文件内容错误不自动换默认值；关系错误不关联“看起来最像”的节点；到期不自动推到明天；冲突不自动删任务。这些容错方式会使用户得到另一份计划，必须避免。

## 5. 取消、重试与进度

- 读取/解析/校验可以取消；后台任务定期检查取消信号，释放缓冲和预览引用。
- 事务写入中只有受控取消：在批次边界检查取消信号并抛出回滚异常；所有已写行仍回滚。取消请求与最终 COMMIT 可能竞争，UI 必须查询回执后说明实际结果，不能无条件显示“已撤销”。
- 提交成功以后“取消导入”不等于删除目标和全部任务，尤其可能已经产生 START。需要另行明确的用户操作，不能做自动清理。
- 锁忙使用有限次数和有上限的退避，每次重新取得事务并重读；语义冲突、空间不足不无限重试。
- 进度可显示读取字节、已校验条数、提交阶段。事务内“已处理 8000/10000”不代表 8000 条已经独立提交；仅最终 COMMIT 才是成功。
- 不把核心 MissionPhase 扩展为“导入中/导入失败”；导入作业状态属于 UI/技术工作流。

## 6. 数据库、磁盘和连接

输入字节不是数据库/WAL/索引所需空间的可靠上界。若平台能查剩余空间，可作保守预检；最终仍必须捕获真实写入失败并回滚。

不在写事务中等待文件选择、AI 请求或用户确认；分块 batch 只用于控制参数、临时对象和驱动限制，不拆成多个对用户可见的提交。

SQLite 只有有限写并发。导入与后台 START 的锁竞争必须测量，不能让大导入长期阻塞到点任务；因此真正开放大规模前必须完成候选查询优化、写锁时间测量及操作提示。

未知数据库版本、迁移失败、损坏关系要中止并保留原库；不能删库重建或把损坏数据当作空库继续导入。

## 7. 提交成功之后仍可能被数据量拖垮

必须验收：

1. 调度器只查需要判断的未开始固定任务，不扫描所有历史材料。
2. 当前列表分页/虚拟构建，摘要使用批量查询，不为每张卡装配全历史。
3. 历史图片只在真实可见时读取，并给缓存容量边界；不能在导入后把旧图全部装进内存。
4. 目标树不要每个节点都查询整份任务列表；一次取得映射或按展开节点加载。
5. 修改一个任务后合并重复刷新，不循环广播 10000 次。
6. 旧的过期异步查询不能覆盖新的选择，离开页面要停止无用工作。

压力库既要测“单个 Goal 多”，也要测“累计多个 Goal 多、执行事件多、正式附件多”。单包限额不能解决分 100 次导入后总量增长的问题。

## 8. 1 万任务采用的暂存方案及更大规模边界

本轮的 1 万任务目标就采用磁盘暂存与流式校验，不能留到以后才考虑：

~~~text
有界流读取 → 临时存储/暂存数据库 → 带索引的跨引用校验
           → 分页预览和明确确认 → 受控提交 → 回执与清理
~~~

暂存不属于正式业务数据，不会被今天页、调度器或统计读取。作业、索引、封存及恢复见[万级导入作业](万级导入作业.md)。首版允许复用已校验封存暂存，但不承诺系统文档来源的任意字节断点续读；来源不能可靠重开时重新读整个文件。

**暂存并不会自动缩短最终复制进业务库的事务。** 若最终数十万条复制仍超出可接受写锁时间，需专门设计“未发布批次不可见、全部读写入口统一过滤、最后一次发布”的可见性协议，覆盖后台调度与崩溃清理。它会改变查询和写入保护，不能现在简单加 staging 标记就算完成。

“把 1 万条拆成十个新目标包”会创建多个 Goal，不满足本次单 Goal 需求。需要同目标持续追加时，先定义目标引用、外部映射和更新契约；不能让用户拆文件后得到意外的几十个目标。

## 9. 本阶段的完成定义

先把[协议](协议与字段.md)、[事务](事务与数据结构.md)及本资源规则收敛为一致契约，再实施小规模完整闭环并完成 1 万规模验收。超限输入必须可恢复地失败；目标规模以内的正确性和性能必须用真实数据量验证。

单次解析成功、整包 INSERT 成功、静态分析通过，都不能代替导入后的长期使用验收。App 整体导入/导出按[后续设计边界](App导入导出衔接.md)承接。
