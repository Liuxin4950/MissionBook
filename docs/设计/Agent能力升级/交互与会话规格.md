# 交互与会话规格

对应 C00、Q01、P01、I01、B01。工作顺序见[工作包与验收](工作包与验收.md)。本篇定义待实现的运行语义与验收条件，类型名可按工程风格落地，含义由本篇统一。

C00 先约定契约和集成位置。实际事件、状态字段与类型在对应完整用户路径实现时加入，避免提前建立只有声明的工具或未使用状态。

## C00 核心事件与交互契约

### 身份关系

| 标识 | 来源与用途 |
| --- | --- |
| sessionId | 现有会话编号，作为存储、权限上下文和对象引用归属 |
| runId | 已有 `turn_started` 的 turnId 统一对外表达为运行编号，事件绑定同一次运行 |
| callId | 模型工具调用编号，原幂等身份继续由 sessionId 与 callId 构成 |
| questionRequestId | 宿主生成，绑定 sessionId、runId、callId 与问题版本 |
| inputId | 发送方在首次提交时生成，失败重试使用同一编号 |
| planId / stepId | 宿主/工具创建的稳定清单与步骤编号，更新沿用同一身份 |
| sourceMessageId | 已接受用户消息编号，供插话来源、分支和记忆依据核对 |

将 `turnId` 对外命名为 runId 时统一文档与 API，不再为同一次运行保存两个独立可写编号。既有日志字段按当前格式策略处理。

### 拟新增的事实事件

| 事件 | 最少载荷 | 提交后的作用 |
| --- | --- | --- |
| question_requested | requestId、runId、callId、questions、revision | 建立待回答请求并暂停该调用 |
| question_answered | requestId、expectedRevision、answerId、answers | 确认答复，生成对应调用的工具结果 |
| question_dismissed | requestId、expectedRevision、reason | 明确跳过或停止，生成对应错误结果 |
| execution_plan_updated | planId、runId、revision、steps、explanation | 更新执行清单投影 |
| input_submitted | inputId、mode、message、submittedAt、targetRunId | 接受一条待消费输入 |
| input_retargeted | inputId、expectedState、mode、targetRunId | 把下一轮输入转为本轮补充 |
| input_withdrawn | inputId、expectedState | 撤回尚未消费的输入 |
| input_consumed | inputId、runId、messageId、boundary | 将队列输入交付给对应运行 |

事件复用已有序列号、时间和版本字段。语义必需事件接受严格校验，业务恢复不能靠忽略未知事件继续。`SessionState.copy/apply`、导出导入、分支、压缩和恢复在 C00 集中接入。

input_consumed 的一次提交同时完成队列出列和消息投影建立，消息内容取自已接受的 input_submitted。不能依赖另一条稍后提交的 message_added 才使消费生效。若为复用现有消息观察器发出通知，该通知由已提交消费事件派生。

### 工具返回与运行停止

当前 `ToolHandler` 返回 `ToolOutput`，普通成功和失败已经有明确语义。新增执行结果必须显式表达“完成结果”与“等待用户”。建议采用统一 `ToolExecutionOutcome`，其中 completed 携带原 `ToolOutput`，awaitingUser 携带结构化问题请求。具体类由 C00 统一建立并同步普通工具工厂、CLI、脚本模型与测试调用方。

`AgentRunResult` 新增 waitingForUser 停止原因，表示该轮已经安全暂停。等待时关闭正在运行的模型流与本轮计时资源，UI 可显示待回答状态。回答后使用原运行关联和待处理调用继续，累计运行预算保存已消耗执行时间，等待用户的时间单独统计。

暂停后的本轮工作仍有逻辑运行身份，继续尝试有可追溯的恢复关联。控制器区分当前有活跃执行和当前有未结算交互，按钮状态从这两类事实派生，避免 isRunning 结束后允许普通发送绕过问题。

现有未知写入核对、普通取消、失败与完成各自有独立状态。继续执行前检查是否仍有结果未知的业务操作。

## Q01 结构化追问

### 用户路径

助手发出问题 → 聊天显示问题卡 → 用户选择或填写 → 点击提交 → 答复确认显示 → 助手继续原工作。多个问题在同一卡片完成，选择控件与提交操作在当前聊天完成。

支持单选、多选、自由填写。用户可显式跳过问题，也可停止当前工作。离开页面和切换会话后，待回答问题和已填写草稿可恢复。

### 请求与答复结构

| 对象 | 字段 |
| --- | --- |
| QuestionRequest | requestId、sessionId、runId、callId、revision、questions、createdAt |
| Question | id、prompt、kind、options、required、allowCustom |
| Option | id、label、description（可选） |
| Answer | questionId、selectedOptionIds、customText |
| Submission | requestId、expectedRevision、answerId、answers |

选项身份使用稳定 id。界面标签变化不改变已选择的业务值。Schema 校验问题编号唯一、单选数量、多选合法编号、必填项、自由输入长度和请求版本。

问题工具建议命名 `askUser`。它属于宿主注册的信息交互能力，问题内容不能携带提权、业务确认或直接操作字段。三档权限下，问题卡提交统一表达用户提供信息。业务工具是否另外确认由当前权限和业务工具规则决定。

### 执行和恢复闭环

```text
模型返回 askUser 调用
  → 校验问题结构 → 持久化 question_requested
  → 保存待处理工具批次与暂停位置 → waitingForUser
  → 用户答复 → 校验请求身份/版本 → 持久化 question_answered
  → 对原 callId 形成 ToolOutput → 处理本批余下调用
  → 纳入工具结果与答复 → 下一次模型请求
```

- 问题与暂停位置提交后才能展示为已接受请求。提交失败时显示可重试错误。
- 同一请求重复提交相同 answerId 返回已接受结果。已回答请求收到冲突答复时显示已处理状态，不重复推进运行。
- 一个模型响应可能同时包含若干工具调用。追问之前已经执行的调用保留结果，追问之后的调用保持 pending，恢复时按原编号与次序继续。
- 对 waitingForUser 的恢复不会触发业务写工具未知结果逻辑。需要在恢复判定处区分交互等待与真实业务执行已开始。
- “跳过”给模型明确的 declined 结果。“停止本轮”终止该轮，并结算本批未执行调用。不得把空答案保存成用户已提供信息。
- 问题卡按 requestId 关联，过期卡、其他会话的答复、已关闭运行的回答不能推进当前会话。
- 问答草稿作为用户本机输入保存，答复正式提交后再成为会话事实和模型上下文。
- 答复保存选项 id、提交时的 label 快照与自由填写原文，建立可追溯的用户输入来源。模型工具结果与用户原文来源各有身份，记忆依据校验要能定位本次用户实际提交的内容。扩展当前最后用户消息查询时，同步 MemoryService 调用与依据回归。
- 答复已提交、对应工具结果尚未提交时退出，恢复只补齐原 callId 的结果。答复与停止竞争通过日志串行和预期状态确定唯一结算。

### UI 与验收

问题卡应有提问内容、选项/输入、提交、跳过和提交状态。多题支持内部滚动，键盘弹出后当前输入和提交操作可触达。已经回答的卡片折叠展示最终答复。

Q01 交付至少覆盖单选、多选、自由填写、草稿重开、重复提交、冲突提交、提交失败、跳过、停止、多工具批次及进程重启后回答。标准/自动/完全权限分别验证追问和业务操作的实际行为。

## P01 执行步骤与进度

### 数据与工具

新增 `updatePlan` 工具，接受 planId、expectedRevision、explanation、steps。首次调用由宿主创建 planId，后续更新使用返回编号。步骤包含 stepId、content、status、relatedCallIds（可选）。status 为 pending、inProgress、completed、blocked、cancelled。

清单事件写入会话日志后返回真实 revision。模型只能更新当前运行拥有的清单。步骤编号稳定，移除或重排在同一完整修订中提交。

### 展示语义

- 输入区上方显示当前步骤、已完成/总数，点击原地展开清单。
- 清单长于可用高度时内部滚动，当前进行项可见。
- 模型报告的分析步骤进展可以显示。步骤关联业务写操作时，完成信息需有已成功提交的调用结果支撑。
- blocked、cancelled 与 failed 的说明来自真实运行和工具状态。运行失败不会自动把剩余步骤变成 completed。
- 本轮结束后可回看其最后清单，下一轮建立独立 planId/runId，历史清单保持可追溯。
- `updatePlan` 属于执行进度控制工具，由宿主写当前会话事实，按注册类型处理，避免在每次进度更新前产生重复业务确认弹层。

P01 验收覆盖修订冲突、重复更新、步骤重排、停止、追问等待、工具失败、未知写入、跨轮和重开。清单中的“保存计划已完成”须能定位真实业务回执。

## I01 运行中补充与下一轮队列

### 输入模式

| 模式 | 用户含义 | 消费时机 |
| --- | --- | --- |
| 本轮补充 steer | 修改或补足当前正在做的工作 | 当前工具批次结算后、下一次模型请求前 |
| 下一轮 queue | 当前工作完成后再处理 | 当前运行正常结束，建立下一轮时 |
| 停止后发送 interrupt | 用户要求先停止当前工作再发送 | 当前运行完成取消结算并检查未知结果后 |

普通空闲发送沿现有入口。运行中发送提供明确默认“补充本轮”和可见的“下一轮处理”选项。用户可以撤回尚未消费的输入、把下一轮消息改为本轮补充。

### 持久化与时序

1. 提交前校验现有文本/附件限制，准备可重开的消息内容与附件引用，持久化 input_submitted 后再清除输入框草稿。
2. 用户输入只有在 input_consumed 提交后才进入对应运行上下文与已接受消息列表。接受/消费共享 inputId，重复投递沿原身份查询状态。
3. 撤回与消费使用同一个日志提交串行入口，预期状态决定谁成功。已经消费的消息显示其实际状态。
4. steer 到达模型生成期间时，当前生成可继续，下一次模型请求前纳入补充。到达工具执行期间时，等待该批已开始操作结算。
5. 模型准备完成本轮时，再次检查尚未消费的 steer。存在补充时继续处理，不能先报告全部完成再遗落补充。
6. 若当前响应仍有未匹配工具调用，先结算整个批次，再插入普通用户补充，保持供应商要求的工具组完整性。
7. 多条 steer 按接受序号消费，保留各自消息身份和原文。下一轮 queue 默认逐条形成后续轮次，可在明确 UI 中合并后发送。
8. 等待问题答复时，可接收补充草稿进入 inbox。正式答复先匹配原 callId，补充在该批结算后的边界消费。

### 停止、异常与恢复

- 用户停止时保留未消费输入并显示“待发送”，用户决定继续或撤回。停止动作不会让队列自动启动新工作。
- 正常完成后自动消费 queue 时，重新检查控制器是否关闭、用户是否停止、会话身份与模型配置是否可用。
- 发生未知写入时，所有后续输入显示等待核对，不能绕过核对创建重复业务操作。
- 进程重开先回放 inbox。仅已提交的 input_consumed 视为消费，未提交的消费可以按同一 inputId 安全重试。
- 补充成为模型有效输入后，更新 `_turnUserMessageId` 等用户来源定位。记忆 basis 校验依据最后一条有效用户原文，不能把队列尚未消费的消息当作已理解事实。
- 主/后台分析、压缩与输入消费有明确串行边界。补充及其技能内容也计入预算，超限保留输入并显示可处理的原因。

I01 验收需要人为控制模型流、工具完成与持久化的时序，覆盖提交与停止、提交与完成、撤回与消费、重启与消费、等待追问、超限附件、重复 inputId 和流断开。检查消息和业务操作分别只被接受一次。

## B01 消息分支、编辑重发与重新回答

### 交互范围

消息菜单提供“从这里分支”。用户消息提供“编辑后重发”，最后一个可重答的助手回答提供“重新回答”。操作后进入新会话，并能回到来源会话。

### 使用既有 fork

- 调用 `AgentSession.fork(throughMessageId)`，按已接受消息确定完整日志前缀。编辑重发和重新回答使用用户问题之前的完整前缀。
- 当前 fork 会拒绝切开工具调用与结果。App 在菜单显示前检查边界，错误时明确说明可选的完整边界。
- 分支元数据保存 parentSessionId、sourceMessageId、branchReason，便于来源导航。它与已有目标/任务/节点引用一起通过 App 会话索引保存或派生。
- 新分支取得独立会话编号、写租约、使用量和运行编号。未提交队列、待回答问题及运行中的子任务按未继承处理，并在新分支中有明确空状态。
- 分支中的历史业务回执可以回看。新工具执行使用新会话与新 callId，只有用户新请求触发后续操作。

### 附件、记忆与模型

编辑重发复用原消息中实际可读的图片和附件，允许用户修改后确认。缺失附件显示具体文件和恢复入口，保留可编辑文字草稿。

分支前缀中的事实、用户原文和上下文来源仍可追溯。需要刷新当前任务和记忆版本的部分经过已有上下文装配，源会话未来消息不能进入分支。模型缺失或图片不兼容时，先让用户选择可用模型再执行新请求。

### 特别场景

重新回答可能再次触发业务工具。重答执行前应展示该轮已有的业务结果，并把成功回执作为事实上下文交给模型。已有命令不因分支重答被视为尚未执行。对会重复产生副作用且无法可靠消解的原问题，重答入口先提供“重述已有结果”或“编辑后发送”，由用户明确新的业务意图。

B01 验收覆盖纯文本、图片、缺附件、工具边界、来源引用、模型删除、原会话写租约、未知结果和有业务副作用的原问题。原会话记录、业务事实与附件内容均检查真实值。
