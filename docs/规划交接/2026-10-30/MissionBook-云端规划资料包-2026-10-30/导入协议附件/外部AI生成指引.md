# 把课标交给外部 AI 生成目标包

更新日期：2026-10-30。当前应用已支持目标包与旧大纲导入，包含校验、分页预览、明确确认、事务和回执；规模与验证边界见实现记录（仓库参考：`docs/设计/目标计划导入/实现与验证记录.md`，未随包附带）。本文指导外部AI生成符合协议的输入，不代替应用校验，也不将生成的计划视为已经执行。

先阅读完整样例（仓库参考：`docs/设计/目标计划导入/examples/课标试运行.goal-package.v1.json`，未随包附带）和[字段协议](协议与字段.md)。把课标、下列实际排期约束以及同目录 JSON Schema 一起交给外部 AI；不要只说“帮我生成学习计划”。

## 用户先提供的约束

| 内容 | 需要明确什么 |
| --- | --- |
| packageId | 给这一次独立计划固定一个唯一名称；重新校验不换，另建副本才换 |
| 课程材料 | 真实课标、章节、要求和已有基础 |
| 日期边界 | 哪天开始、哪天结束 |
| 时区 | 如 Asia/Shanghai |
| 可用时间 | 每周哪几天、具体时段、每天最多多久 |
| 排除项 | 放假、考试、已有安排、不能学习的日期 |
| 任务粒度 | 每次 30/45/60 分钟等，以及是否允许拆分 |
| 启动方式 | 固定几点自动开始，还是只安排日期后手动开始 |
| 材料要求 | 哪些课要截图/代码/文字，何时截止，哪些只自报 |
| 总量 | 本次先试运行 5–20 项，确认流程后再扩大 |

原课标是内容依据，可用时间是排期依据，两者不足时都不能由 AI 当作事实猜定。可以让 AI 先建议课程粒度，由用户决定后再生成正式 JSON。

## 可复制提示词

~~~text
你负责将我给出的真实课标与排期约束，转换为 MissionBook 的目标任务导入包。
请先核对信息是否足够；缺少开始日期、时区、可用时段或必要材料要求时，
先用简短问题让我补充。约束齐全后，只输出一个严格 JSON 对象，不带 Markdown。

我会提供：
1. 真实课标或课程大纲；
2. packageId、计划开始/结束日期、IANA 时区；
3. 每周可用日期与时段、单次时长、每日负荷上限及排除日期；
4. FIXED/FLEXIBLE 的选择和各课材料要求；
5. mission-book.goal-package.v1.schema.json 与示例。

请严格执行以下转换规则：

一、根对象只允许：
schema、version、packageId、goal、defaults、nodes、missions。
schema 固定为 "mission-book.goal-package"，version 为整数 1。
packageId 使用我提供的值，修正当前文件时不要自动更换。

二、课程总体方向放 goal。
模块、章节、知识点放 nodes 的树；节点包含 key/title，可选 description/children。
node key 在整棵树内唯一，使用小写字母、数字、点、下划线、短横线。
保留课标中的重要内容，不把所有原文塞进一个节点说明来冒充完整分解。

三、每次真正要执行的课次或练习创建一个 mission。
mission 包含 key、title、schedule，可选 nodeKey、description、why、
verificationPolicy、executionPlan。
mission key 在任务集合中唯一；nodeKey 必须引用本包存在的节点。
同一知识点可以有多次不同日期的练习；不要强制每个章节只有一个任务。
综合回顾可以省略 nodeKey，表示直接属于目标。

四、defaults 必须明确 timeZone、plannedDurationMinutes、verificationPolicy。
每个 schedule 都必须明确 scheduledDate 和 timePolicy。
FIXED 必须有带明确时区偏移或 Z 的 fixedStartAt，FLEXIBLE 不得出现该字段。
日期必须真实存在，星期、偏移与 IANA 时区一致，时长是整数分钟。
不要输出“下周一”“晚上”“第 2 周”等无法直接落地的时间。

五、把有限的重复课程按具体日期展开为多条 mission。
落实开始/结束边界、节假日、单双周和排除日期，不输出 recurrence 或无限规则。
遵守可用时间，核对包内每个固定时段和每日总负荷，不擅自占用空闲以外的时间。

六、executionPlan 可含 objective、steps、verificationCriteria、notes。
objective 是可观察的本次结果；steps 是有顺序、可实际执行的文字步骤。
内容具体到能开始做，不要只写“学习该章”“掌握知识”。
不要编造我没有表达的个人动机、已有能力、学习结果或实际执行情况。

七、验证策略只允许 SELF_REPORT / OPTIONAL_EVIDENCE / REQUIRED_EVIDENCE。
强制材料必须有非空 verificationCriteria，说明要提交什么及怎样自查。
只有强制材料任务可写 evidenceDeadlineAt；可省略以采用排期日次日零点，
但跨午夜或需要更多提交时间时，应明确安排合法的更晚截止。
可选材料和自报不得出现 evidenceDeadlineAt。

八、不要输出数据库 ID、status、phase、createdAt、实际开始/结束、
执行事件、材料内容、失败记录、完成率、掌握度或 AI 分数。
不要输出自动结束、抢占执行、逐任务提醒、dependsOn 或其他协议外字段。
空的可选内容省略；不要用 null 或占位字符串代替未知信息。

九、最终生成前自行核对：
所有课标要求是否有明确节点；课次是否足够覆盖这些内容；
节点和任务 key 是否唯一；nodeKey 是否存在；
所有日期和星期是否正确；固定时段是否重叠；
默认值和覆盖值是否正确；材料方向及截止是否匹配；
总任务数、每天分钟数是否符合我给出的上限。
不能因为 JSON 格式正确就声称计划已可行或我已经掌握课程。
~~~

## 生成以后怎样检查

先检查内容是否忠实覆盖课标，再检查可用时段和任务数量；这两件事无法单靠 Schema 确认。然后检查结构、引用、日期、时区、材料规则及冲突。正式软件导入仍必须预览确认，外部 AI 的自查不替代应用校验。

第一次建议包含：一个固定自报任务、一个自选可选材料任务、一个固定强制材料任务，以及至少一个同节点的后续练习。通过真实执行、结束报告、材料和重开历史确认流程后，再导入整学期。

不要直接把示例文件当成自己的课标。示例日期为 2026 年 11 月，晚于该日期使用时应重新排期并重新检查截止。

## 一万任务不要依赖一次超长回答

用户的一万任务目标是 App 的数据承载要求，不要求外部 AI 在一次对话里枚举一万条 JSON。超长输出容易出现截断、重复 key、课次遗漏和日期计算错误；不能靠在截断文本后补一个括号就当成合法计划。

建议区分两种生成工作：

1. AI 负责理解课标，提出模块/知识点、每次目标、执行步骤、材料标准及有限排期约束；先由用户确认内容和粒度。
2. 外部确定性生成工具按这些约束展开具体日期、跳过例外、分配唯一 key、计算总量及冲突，流式写成一个正式 goal-package 文件。它可以是外部脚本，不需要内置 AI 或新增领域 Plan 表。

如果让 AI 分模块生成片段，外部组装工具需统一节点/任务键空间、检查重复和引用，保留一个固定 packageId，核对预期课次总数，最终才输出一份完整文件。片段不是本协议的新入口，不能把十个片段直接各导入一次，造成十个 Goal。

大规模生成仍只输出本协议已有字段，不能把作者侧模板或 recurrence 附加到正式包。运行时模板和持续更新需求见排期设计（仓库参考：`docs/设计/目标计划导入/排期与导入配置.md`，未随包附带），App 接收端仍按万级作业（仓库参考：`docs/设计/目标计划导入/万级导入作业.md`，未随包附带）实施流读与完整校验。
